# ami's log 방향 논의 메모 (임시)

> 상태: **임시 메모, 결정 아님.** 다음 논의를 이어가기 위해 지금까지 나온 이야기를 모아 둔 문서다. 방향이 확정되면 이 문서를 정식 기획 문서로 옮기거나 지운다
> 출처: 2026-10-12 논의. 기획 쪽에서 나오고 있는 방향과, 그에 대한 오너의 개인 의견, discovery 쪽 검토 의견을 나눠 적는다. 오너 의견도 **개인 의견이지 결정이 아니다**
> 관련 문서: `new-type/knowledge-agent-recommendation.md`(이하 knowledge 문서), `new-type/shout-to-people.md`(이하 shout 문서, PR 대기 중). 두 문서는 topic이 있다는 전제로 쓰였다. 이 메모의 방향이 확정되면 둘 다 다시 써야 한다(§7)
> 이 문서는 아직 어떤 문서도 고치지 않는다

## 0. 요약

- 유저의 에이전트 이름은 **ami**가 될 것 같다.
- 유저가 ami와 대화하며 어떤 주제에 대한 정보가 쌓이면 **ami's log**가 만들어진다. 요약·정리되어 publish되는, SNS의 post 같은 것이다.
- log는 세 가지에 쓰인다.
  - 유저의 프로필 페이지(**portal**)를 꾸미는 재료
  - 다른 유저가 내 ami와 대화할 때 ami가 쓰는 재료
  - 추천의 재료
- **기존 topic은 없어질 것 같다.** log에 자연어 태그가 붙는다. 시스템이 붙이는 것과 유저가 붙이는 것이 있다. topic별 성숙도·점수도 함께 사라진다.
- 추천은 세 단계다.
  1. 다른 유저들의 log로 **답을 직접 만들고**, 답에 쓰인 log의 유저와 대화해 보라고 함께 추천한다.
  2. 답은 못 만들지만 대화해 볼 만한 유저를 **답 없이** 추천한다.
  3. 그것도 어려우면 **shout**로 답할 수 있을 것 같은 유저에게 질문을 보내고, 받은 유저가 답한다.
- log를 어디에 어떻게 저장할지는 정해진 바가 없다.

discovery 쪽 판단: 지금까지 논의한 것과 잘 맞고, 구조는 오히려 단순해진다. 다만 지금 discovery 코드의 큰 부분이 topic 전제라서 확정되면 재설계 규모가 크다.

## 1. 용어

| 용어 | 뜻 |
|---|---|
| ami | 유저의 에이전트 시스템 이름(가칭). |
| ami's log (이하 log) | ami와의 대화에서 만들어져, 유저가 확인한 뒤 publish되는 요약·정리 글. post에 가깝다. |
| portal | 유저의 프로필 페이지. 내부 임시 이름이다. log를 재료로 콜라주 등 어떤 형태로든 꾸며지고, 일부 log가 직접 보인다. |
| system tag | 시스템이 log에 자동으로 붙이는 태그. 지금의 topic 역할을 맡는 후보다. 유저에게 보일 수도 안 보일 수도 있다. |
| 유저 태그 | 유저가 직접 입력한 자유 형식 태그. |
| 답 생성 추천 | 추천 1단계. 다른 유저들의 log로 답을 만들고 출처 유저를 함께 추천한다. knowledge 문서 열린 항목 33(answer mode)이 주 경로가 된 것이다. |

## 2. 지금 구조와의 대응

### 2-1. 하나로 합쳐지는 것

지금은 비슷한 일을 하는 것이 둘 있다.
- **topic**: 공개 범위의 단위이자 추천의 근거.
- **lived-knowledge 기록**: 답의 재료.

log는 이 둘을 하나로 합친다. 유저가 보는 것, ami가 대화에 쓰는 것, 추천에 쓰는 것이 모두 같은 log다.

"공개된 것만 추천 근거로 쓴다"는 지금까지의 원칙은 더 자연스러워진다. knowledge 문서 열린 항목 33에서 전제 조건으로 남겨 둔 동의 문제(남의 지식으로 답을 만들어도 되는가)도 쉬워진다. 유저가 확인하고 publish한 것이 곧 동의이기 때문이다.

### 2-2. 추천 세 단계의 대응

| 새 흐름 | 지금 문서에서 대응하는 것 |
|---|---|
| 1. 답을 만들고 출처 유저를 추천 | knowledge 문서 열린 항목 33(answer mode) → 주 경로로 승격 |
| 2. 답 없이 대화해 볼 유저를 추천 | knowledge 추천(타입 ④) |
| 3. shout | shout 문서 |

knowledge 문서의 파이프라인 뼈대(검색 → judge가 covers 판정 → 실패하면 다음 단계)는 재사용할 수 있다. 바뀌는 것은 검색 단위가 log라는 점이다.

### 2-3. topic이 사라지면 대체해야 하는 것

| topic이 하던 일 | 대체 후보 |
|---|---|
| 검색 대상(`visible_topic_rows`, 타입 ① 매칭, R69 하위 topic 매칭) | system tag 일치 + log 본문 임베딩 검색 + 키워드 검색(§4) |
| 공개 범위(visibility가 topic을 따름) | **log 단위 공개 범위.** 공개/친구/비공개를 누가 어떻게 정하는지 결정해야 한다 |
| 품질 신호(`topic_score`, `topic_maturity`) | log 단위 신호. 몇 번의 대화에서 나왔는지, 최근성, 유저가 직접 손봤는지, 답에 쓰여 도움이 됐다는 피드백 등 |
| 카탈로그 계층(shout 차수 확장, 상위·형제 topic) | 계층 대신 태그 간 유사도, 같은 log에 함께 붙는 빈도(동시 출현), 또는 유사도 임계값을 단계적으로 낮추기 |
| 추천 이유 문구("위스키를 공개 관심사로 두셔서") | "이 log를 쓰셔서" 또는 태그. 오히려 더 구체적이 된다 |

### 2-4. 그대로 쓸 수 있는 것과 쓸모없어지는 것

- **그대로 쓸 수 있다** (topic과 무관):
  - `friends`
  - `interactions` / `room_turns`
  - `popularity`
  - `attributions`
  - `agents`의 활동 시각
  - shout 원장(shout 문서 §8)
- **쓸모없어진다**: `visible_topic_rows`, `catalog_edges`, topic 기반 CF, 그리고 그 위에 쌓은 R 결정 상당수.

## 3. 열린 질문과 지금까지의 의견

각 항목에서 "오너 의견"은 2026-10-12 오너의 개인 의견이고 결정이 아니다. "검토 의견"은 discovery 쪽 의견이다.

### 3-1. log의 단위와 생성 시점

- **오너 의견**
  - 언제 만들지는 아직 말할 수 없다.
  - 같은 주제로 대화가 더 쌓이면 기존 log를 갱신하기보다 **새 log를 만드는 형태**일 것 같다. 새 post가 올라가는 느낌이다.
  - 새 log를 만들 때 기존 log를 참고해서 쓸 수는 있을 것이다.
- **검토 의견**
  - 같은 사람의 log가 여러 개 검색된다. 사람을 추천할 때는 **owner 단위로 묶어야** 한 사람이 목록을 다 차지하지 않는다.
  - 옛 log와 새 log가 다를 수 있다(예: 예전엔 피트를 싫어했는데 지금은 좋아함). 답을 만들 때 **최근 log를 우선하는 기준**이 필요하다.
  - post라도 수정·삭제는 일어난다. 수정·삭제 이벤트는 여전히 필요하다(§5).
  - 기록이 계속 쌓이는 문제(knowledge 문서 열린 항목 32)는 다시 생긴다. 다만 단위가 문장보다 훨씬 굵어서 부담은 작다.

### 3-2. publish 전 유저 확인

- **오너 의견**: 유저 확인을 거친다.
- **검토 의견**
  - 동의 문제가 깔끔해진다.
  - 확인 화면에서 이 log가 portal에 보일 뿐 아니라 **다른 사람의 질문에 답하는 재료로도 쓰인다**는 것을 알려야 한다. 그래야 인용됐을 때 유저가 놀라지 않는다.
  - 유저가 거절한 초안은 publish되지 않으므로 discovery로는 아예 오지 않는다.

### 3-3. 보여주는 용도와 답하는 용도의 충돌

- **검토 의견**
  - portal에 쓰는 log는 짧고 보기 좋아야 한다.
  - 답의 재료로 쓰는 log는 구체적이어야 한다. knowledge 문서 열린 항목 33에서 이미 "요약은 얇다"고 지적했다.
  - 하나의 log에 **표시용 레이어와 본문 레이어**를 같이 두는 구조를 고려할 만하다.
- **오너 의견**: 좋은 지적이라 참고하겠다.

### 3-4. 태그의 역할

- **오너 의견**
  - system tag를 지금의 topic과 같은 역할로 쓰고, 유저 태그도 있다고 하면, 이걸로 검색해도 좋지 않을까.
  - system tag는 유저에게 보일 수도 안 보일 수도 있다.
  - 정규화가 꼭 필요한지는 모르겠다. 유저가 자유 입력한 것 자체에도 의미가 있고, UX상 결국 비슷한 태그를 쓰게 되지 않을까. 이상한 태그를 다는 건 유저의 몫이다.
- **검토 의견**: §4에 정리했다.

### 3-5. lived-knowledge 기록과의 관계

- **오너 의견**: log가 lived-knowledge를 대체하는 형태가 될 것 같다.
- **검토 의견**
  - 기록을 추출하던 파이프라인(knowledge 문서 §7)은 **log를 생성하는 쪽 일**이 된다. 소유 서비스가 바뀔 수도 있다.
  - discovery는 **인덱스·검색·순위**만 맡게 된다.
  - 기록에 있던 `kinds[]`(경험, 의견 등)는 log의 system tag나 메타데이터로 옮기면 된다.
  - 출처 표시는 문장 단위가 아니라 log 단위가 된다. 사람을 추천하는 데는 그 정도로 충분하다.
  - 이미 scaffold한 lived-knowledge repo와 knowledge 문서의 수집 부분은 확정되면 정리해야 한다.

### 3-6. 초기에 log가 없는 시기(cold start)

- **오너 의견**: 아직 모르겠다. 기획팀에서 더 자세한 기획이 필요하다.
- **검토 의견**
  - log가 쌓이기 전에는 추천 1·2단계가 거의 실패하고 shout 비중이 커진다.
  - shout 답이 답한 사람의 **log 초안**이 되는 구조라면, shout가 초기에 log를 채우는 경로가 될 수 있다. shout 문서 §7에서 답을 경험 기록으로 쌓는 것과 같은 논리다.

### 3-7. 저장 소유권

- **검토 의견(제안한 원칙)**
  - log 원본은 **한 서비스가 소유**한다(log 서비스든 bourbon-api든).
  - discovery는 지금 topic row를 미러링하듯 이벤트로 받아 **검색 인덱스(임베딩)와 공개 범위 사본**만 가진다.
  - 이렇게 하면 "discovery에는 공개된 것의 사본만 있다"는 지금의 경계가 그대로 유지된다.
- **오너 의견**: 이 원칙은 적당해 보인다.

## 4. 태그와 검색 (검토 의견)

### 4-1. 태그를 임베딩하면 약하다

짧은 태그 하나만 임베딩해서 검색하면 약하다.
- **문맥이 없다.** "피트"는 위스키의 피트, 길이 단위, 사람 이름일 수 있다.
- **길이가 맞지 않는다.** 질문은 문장이고 태그는 단어다. "셰리 캐스크인데 너무 달지 않은 거 추천해줘"와 태그 `셰리`의 유사도는 생각보다 낮고 순위도 불안정하다.
- **같은 범주끼리 뭉친다.** 단어 임베딩은 "위스키", "와인", "칵테일"을 서로 가깝게 둬서 구체적인 구분이 흐려진다.

태그를 **정확히 일치**시키거나 **키워드 검색**으로 쓰면 짧은 것은 문제가 되지 않는다. 오너 의견(태그로 검색)과는 이 방식으로 맞춰진다.

### 4-2. 정규화가 필요한 곳은 system tag다

- **system tag**
  - topic 역할을 하려면 같은 것에는 늘 같은 태그가 붙어야 한다.
  - LLM은 호출할 때마다 표기가 달라진다(`셰리 캐스크`, `셰리캐스크`, `Sherry cask`).
  - 그래서 LLM이 **기존 태그 목록에서 먼저 고르고**, 정말 없을 때만 새로 만들게 한다. 그러면 따로 정규화하지 않아도 만드는 순간 정규화된 상태가 된다.
- **유저 태그**
  - 오너 의견대로 자유 입력 자체에 의미가 있다.
  - 입력할 때 기존 태그를 **자동완성으로 제안**하면 UX만으로 표기가 모인다.
  - 이상한 태그는 그 유저 본인의 노출만 손해 본다.
  - 주의할 점: 유저 태그를 남의 질문 순위에 크게 반영하면, 인기 태그를 잔뜩 달아 노출을 노리는 유저가 생길 수 있다. **가산을 작게** 두는 편이 안전하다.

### 4-3. 검색 역할 나누기

| 무엇으로 | 역할 |
|---|---|
| system tag | 구조화된 일치. 지금의 topic 매칭을 대신한다 |
| 유저 태그 | 작은 가산, portal 표시 |
| log 본문 임베딩 | 의미 검색. 태그가 놓치는 것을 잡는다 |
| 키워드 검색(BM25 등) | 고유명사(증류소, 제품명) 일치. 임베딩과 함께 하이브리드로 쓴다 |

system tag에 계층이 없으면 "넓히기"(shout 차수 확장, R69 하위 topic 매칭)를 다른 방식으로 해야 한다. §2-3의 대체 후보 중에서 고른다.

## 5. log 사본을 discovery에 두는 방식 (검토 의견)

오너 제안: log는 다른 서비스가 임베딩 없이 저장한다. discovery는 이벤트를 받아 임베딩을 만들고 log의 key를 함께 저장해 추적한다.

이 방향이 좋다고 봤다. 지금 topic row를 다루는 방식과 같고, 이벤트 worker를 소비하는 쪽 repo에 두는 기존 관례와도 맞는다. 다만 아래가 필요하다.

### 5-1. 생성 말고도 받아야 할 이벤트

| 이벤트 | 받지 않으면 |
|---|---|
| 생성 | — |
| 수정 | 옛 내용으로 검색되고, 옛 내용이 답에 인용된다 |
| 삭제 | 유저가 지운 log가 남의 답에 계속 쓰인다. **개인정보 문제라 가장 중요하다** |
| 공개 범위 변경 | 비공개로 돌린 log가 계속 추천 근거로 쓰인다 |
| 탈퇴 | 지금 `departed_users`가 하는 일을 log에도 해야 한다 |

이벤트는 순서가 바뀌어 도착할 수 있다. 이벤트에 `version`(또는 `updated_at`)을 담고, 받는 쪽은 더 새로운 버전일 때만 반영한다.

### 5-2. 이벤트에 무엇을 담나

- **key만 담고 본문은 log 서비스에서 조회 (권장)**: 항상 최신 본문을 읽고, 원본이 한 곳에만 있다. log 서비스에 읽기 API가 필요하다.
- **이벤트에 본문까지 담기**: 조회 호출이 필요 없지만 이벤트 큐에 본문이 남는다.

어느 쪽이든 log 서비스의 읽기 API(단건 조회, 목록 조회)는 결국 필요하다. 임베딩 모델을 바꿀 때 전체를 다시 임베딩해야 하고, 누락분도 맞춰야 하기 때문이다.

### 5-3. discovery에 저장할 것

| 필드 | 이유 |
|---|---|
| `log_id`, `owner_user_id` | 추적, 출처 표시 |
| `version` | 순서 역전 방지 |
| `visibility` | 검색할 때 공개 범위 필터링 |
| `embedding`, `embedding_model` | 모델을 바꿀 때 다시 임베딩할 대상 찾기 |
| system tag, 유저 태그 | 일치·가산 |
| `embedded_at`, 상태(pending/done/failed) | 실패 추적 |

- **본문을 저장할지는 정해야 한다.**
  - 저장하지 않으면 원본이 한 곳에 있다는 점이 깔끔하게 지켜진다.
  - 키워드 검색을 하려면 검색용 텍스트가 discovery에 있어야 한다.
  - 저장한다면 검색 인덱스 용도로만 두고, 삭제 이벤트에 확실히 함께 지운다는 조건을 붙이는 것이 현실적이다.
- **저장소**: PostgreSQL + pgvector가 자연스럽다. 이미 PostgreSQL을 쓰고 있고, 공개 범위 필터와 벡터 검색을 한 쿼리로 할 수 있다.

### 5-4. 실패 처리

deferq에는 재시도와 DLQ가 없다. 임베딩 호출(e3llm)이 실패하면 그 이벤트는 사라진다. 그래서 두 가지를 둔다.
- 이벤트를 받으면 먼저 `pending` row를 쓰고, 임베딩은 그다음에 한다. 실패한 것은 worker loop가 재시도한다.
- 주기적으로 log 서비스 목록과 대조해 누락분을 채운다.

### 5-5. 답을 만들 때는 원본을 다시 확인

discovery의 사본은 늘 약간 늦다. 검색은 사본으로 하더라도, 답의 재료로 넘기기 직전에는 log 서비스에서 해당 key들을 다시 조회한다. 삭제됐거나 비공개로 바뀐 것은 빼고, 본문은 이때 최신으로 가져온다. 그러면 이벤트가 늦게 도착하는 사이에도 지운 log가 인용되지 않는다.
