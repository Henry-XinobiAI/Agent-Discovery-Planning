## 1. 한 문장으로

유저들이 쓴 **note**를 받아 두었다가, 누군가 질문하면 **그 note로 답할 재료를 찾아 주고**, 그걸로 안 되면 **답해 줄 수 있을 것 같은 사람을 찾아 주는** 서비스다. 이 서비스가 discovery다.

## 2. 무엇을 하는 서비스인가

### 2-1. 등장하는 것

| 이름 | 무엇 |
|---|---|
| ami | 유저마다 있는 에이전트. 유저와 대화하고, 다른 유저의 질문에도 답한다 |
| note | ami와의 대화에서 만들어져, 유저가 확인한 뒤 공개하는 글. SNS의 post에 가깝다. 실험에서는 한국어 한 문단으로 만들었다. 표시용 요약을 따로 둘지는 정하지 않았다 |
| portal | 유저의 프로필 페이지(내부 임시 이름). note를 재료로 꾸며진다 |
| note 서비스 | note를 만들고 원본을 저장하는 서비스. discovery가 아니다. 어느 서비스가 맡을지는 정하지 않았다 |
| bourbon-agent | 유저의 질문을 받고 ami의 답을 만드는 쪽. 언제 discovery를 부를지 정한다 |
| discovery | 이 문서의 주인공. note 사본을 받아 검색할 수 있게 만들고, 질문이 오면 note와 사람을 찾는다 |

### 2-2. 질문 하나가 처리되는 흐름

유저가 자기 ami에게 질문하면 세 단계로 내려간다.

1. **내 ami가 직접 답한다.** 답할 수 있는지는 bourbon-agent가 판단한다. discovery는 관여하지 않는다.
2. **다른 사람들의 note로 답한다.**
   - discovery가 질문과 맞는 note를 찾아 넘긴다.
   - ami가 그 note로 답을 만들고, 출처 note를 쓴 사람을 "이 사람과 이야기해 보라"고 함께 추천한다.
   - 답을 만들 만큼은 안 되면 사람만 추천한다.
3. **shout한다.**
   - 쓴 note만으로는 답이 없으면, 답해 줄 수 있고 관심도 있을 것 같은 사람들에게 질문을 보낸다. 받은 사람이 직접 답한다.
   - 몇 명에게 보낼지는 유저가 확성기 소리를 키우듯 고른다(shout 범위).

이와 별개로 유저가 **처음부터 직접 shout를 던질** 수도 있다. 이때도 3과 같은 방식으로 사람을 고른다.

discovery 안의 note 검색은 **하나**이고, 입구가 **둘**이다(메모 §9-1, §10-1). 하나는 ami와 대화하다 나온 질문이고, 다른 하나는 유저가 직접 던지는 shout다. 검색 한 번의 결과에 2단계용 note와 사람, 3단계용 shout 범위별 후보가 함께 담긴다. 그래서 단계마다 같은 후보를 기준으로 판단하고, 지연도 한 번만 든다.

```
[입구 1] ami와 대화 중의 질문
   ├─ 1. 내 ami가 답할 수 있나? (bourbon-agent가 판단)
   │       └ 못 하면 ↓
   ├─ 2. 다른 사람의 note로 답하기 ── 검색 결과의 상위 note 8개 → ami가 답 + 출처 사람 추천
   │       └ 맞는 note가 없으면 ↓
   └─ 3. shout ─────────────────── 검색 결과의 shout 범위별 후보 → 질문 전달

[입구 2] 유저가 직접 던지는 shout ─── 질문과 범위를 골라 바로 던짐 → 3과 같은 방식으로 사람 고르기
```

## 3. note가 오면 discovery는 무엇을 하나

> §3~§6은 메모 §12-1 등의 **검토 의견(제안)**을 정리한 것이다. 오너가 확정한 것은 §6-2의 재순위 B1 채택 하나이고, 그것도 다시 볼지 정하는 중이다(§8).

### 3-1. 원본은 note 서비스, discovery는 사본

note의 원본은 note 서비스가 갖는다. discovery는 이벤트를 받아 **검색용 사본**을 만든다. 사본에는 아래를 둔다(메모 §5-3, §12-3).
- note id, 쓴 사람(owner) id, 버전, 공개 범위
- embedding과 그 모델 이름
- tag와 entity
- 처리 상태

### 3-2. 받는 이벤트

| 이벤트 | discovery가 하는 일 | 받지 않으면 |
|---|---|---|
| 생성 | 사본을 만들고 embedding·tag·entity를 붙인다 | 검색에 나오지 않는다 |
| 수정 | 다시 embedding하고 다시 tag한다 | 옛 내용으로 검색되고 옛 내용이 인용된다 |
| 삭제 | 사본을 지운다 | 지운 note가 남의 답에 계속 쓰인다. **개인정보 문제라 가장 중요하다** |
| 공개 범위 변경 | 검색 대상에서 빼거나 다시 넣는다 | 비공개로 돌린 note가 추천 근거로 쓰인다 |
| 탈퇴 | 그 유저의 사본을 모두 뺀다 | 탈퇴한 유저가 추천된다 |

### 3-3. 생성 이벤트를 받았을 때의 순서

1. **먼저 "처리 중" 상태로 기록한다.** 이벤트 큐(deferq)에는 재시도가 없다. 기록부터 해 두면 뒤의 단계가 실패해도 주기 작업이 다시 집어 갈 수 있다.
2. **note 서비스에서 본문을 읽는다.** 이벤트에는 key만 담는 쪽을 권한다(메모 §5-2).
3. **embedding을 만든다.** 본문을 숫자 벡터로 바꾼다(§5). 이때부터 tag가 붙기 전이라도 검색 후보에 들어간다(메모 §12-4).
4. **tag를 붙인다.** 등록된 tag 3~6개와 카탈로그 topic 1~3개다(§4).
5. **entity를 뽑는다.** 지명, 상품명, 상호명, 작품명 같은 고유명사다(§4).
6. **"완료"로 바꾼다.**

빠지는 것이 없게 세 가지를 더 둔다.
- **순서가 뒤바뀐 이벤트:** 이벤트는 순서가 바뀌어 올 수 있다. 버전을 함께 저장하고, 더 새로운 버전일 때만 반영한다.
- **빠진 note 채우기:** 주기적으로 note 서비스의 목록과 대조해 빠진 것을 채운다(메모 §5-4).
- **답에 쓰기 직전에 원본을 다시 확인한다:** 사본은 늘 조금 늦다. 그래서 답의 재료로 넘기기 직전에 note 서비스에서 다시 조회한다. 그사이 지워졌거나 비공개로 바뀐 note는 뺀다(메모 §5-5).

### 3-4. tag를 왜 discovery가 붙이나

> 오너 의견에 검토 의견이 동의한 것이다. 결정은 아니다(메모 §12-4).

note 서비스가 붙일 수도 있다. 하지만 실험해 보니 tag는 note의 의미라기보다 **검색 인덱스**에 가깝다.
- tag 체계, 프롬프트, 모델은 검색 결과를 보며 계속 고칠 대상이다. 실험 몇 번 만에도 여러 번 바뀌었다.
- 체계를 바꾸면 전체 note를 다시 tag해야 한다. 사본을 가진 discovery가 자기 일정대로 다시 돌리는 편이 낫다.
- note 서비스는 note 만들기에만 집중하고, discovery 사정으로 배포할 일이 없어진다.

## 4. tag란 무엇이고, 어떤 것이 있나

### 4-1. tag가 하는 일

tag는 note에 붙는 짧은 꼬리표다. "이 note가 무엇에 관한 것인가"를 몇 단어로 적는다. 하는 일은 셋이다.
- **검색 범위 좁히기(필터):** 질문과 같은 tag가 있는 note만 후보로 남긴다.
- **사람 고르기:** 어떤 사람이 어떤 tag의 note를 얼마나 썼는지가 그 사람의 프로필이 된다.
- **shout 범위 나누기:** tag의 넓이로 "작게 / 보통 / 크게" 단계를 만든다.

note의 순위는 tag가 아니라 embedding이 매긴다(§5). 사람의 순위에는 tag 프로필 점수도 들어간다(§6-2).

### 4-2. 종류

| 종류 | 예 | 어디서 오나 | 언어 | 쓰는 곳 |
|---|---|---|---|---|
| **등록된 tag** (주축) | `sourdough starter`, `weight loss`, `bouldering` | LLM이 지금까지 쓰인 tag 목록에서 고른다. 맞는 것이 없을 때만 새로 만든다 | 키는 영어. 처음 등록할 때 한국어 표시 이름을 함께 정해 고정한다 | 검색 필터, 사람 프로필, shout 범위 |
| **카탈로그 topic** (보완) | 건강, 반려동물 같은 계층형 주제 | 이미 있는 topic 카탈로그(bourbon-topic-api)에서 고른다 | topic id. 표시는 카탈로그의 한국어 이름 | 검색 필터의 보완, portal 분류와 통계 |
| **entity** (고유명사) | `제주`, `이마트`, `GlenDronach` | note에서 LLM이 뽑는다. 이미 등록된 것과 같은지 먼저 확인한다 | 그 대상의 원래 언어. 다른 표기는 별칭에 둔다 | 질문에 고유명사가 있을 때만 검색에 더한다 |
| 유저 태그 (나중) | 유저가 쓴 그대로 | 유저 | 입력한 그대로 | 첫 제품에는 없다 |

tag와 entity의 언어는 오너 의견에 검토 의견이 동의한 것이다. 결정은 아니다(메모 §12-5).

### 4-3. 등록된 tag의 "넓이"와 shout 범위

등록된 tag는 처음 등록될 때 넓이를 하나 받는다. 그 뒤로는 바뀌지 않는다.

| 넓이 | 실험에 실제로 있던 tag | shout 범위 |
|---|---|---|
| specific (좁음) | `sourdough starter`, `mounjaro` | **작게**: 질문의 specific tag가 붙은 note를 쓴 사람 |
| mid (중간) | `weight loss`, `bouldering` | **보통**: 작게 + 질문의 mid tag가 붙은 note를 쓴 사람 |
| broad (넓음) | `baking`, `health` | **크게**: 보통 + 질문의 broad tag가 붙은 note를 쓴 사람 |

한 note에 넓이가 다른 tag를 섞어 단다. 예를 들어 마운자로 이야기에는 `mounjaro`, `weight loss`, `health`를 함께 붙일 수 있다. 그러면 질문 하나로 유저에게 이렇게 보여줄 수 있다(메모 §8-6).

> 🔈 작게: 마운자로에 대해 note를 남긴 사람들에게 (약 4명)

topic 계층이 하던 "좁은 것에서 넓은 것으로"를 tag의 넓이가 대신한다.

### 4-4. 고유명사는 왜 tag가 아니라 entity인가

- **사는 곳이 tag로 새어 든다.**
  - 실험에서 장소 규칙 없이 붙이면 `jeju` tag가 note 60개에 붙었는데, 그중 57개는 제주에 사는 사람이 쓴 다른 주제의 note였다.
  - "글쓴이가 사는 곳은 붙이지 말라"는 프롬프트 규칙을 넣어도 31개 중 28개가 그랬다(메모 §12-3).
- **표기가 흔들린다.** 제주/Jeju/제주도, 스타벅스/스벅/Starbucks처럼 같은 대상이 여러 표기로 나온다. 정규형과 별칭으로 묶어 두면 키워드 검색이 놓치는 것을 받는다.
- **식별 정보다.** 상호명과 지명은 거주지·직장·단골집이 되기 쉽다. 그래서 tag와 따로 저장하고, 보여주는 곳(portal, "왜 이 사람인지")에는 드러내지 않는다.

## 5. embedding은 무엇을 하나

embedding은 글을 숫자 벡터로 바꾼 것이다. 뜻이 가까운 글끼리 벡터도 가깝다. 실험에서는 `gemini-embedding-001`(768차원)을 썼다. `text-embedding-3-small`보다 한국어에서 확실히 나았다(모호한 질문의 hit@5가 0.79에 그쳤다, 실험 §2).

| 어디에 | 무엇과 무엇을 비교하나 | 왜 |
|---|---|---|
| note 검색의 순위 | 질문 ↔ note 본문 | tag로 좁힌 후보를 뜻이 가까운 순서로 줄 세운다 |
| 사람 고르기 | 질문 ↔ 그 사람의 note 중 가장 가까운 3개 | tag 프로필만으로는 놓치는, 실제로 비슷한 글을 쓴 사람을 끌어올린다 |
| tag 고를 때 보여줄 tag 뽑기 | note 본문 ↔ 등록된 tag | 목록이 커지면 가까운 tag만 보여주기 위해서다. 방식은 아직 정하는 중이다(§8) |
| 동의어·entity 후보 뽑기 | tag·entity ↔ tag·entity | "같은 것일 수 있는" 후보를 뽑는다. 같은지는 LLM이 판정한다 |

- **짧은 단어끼리의 비교는 조심한다.** `java`, `football` 같은 한두 단어끼리의 embedding은 뜻을 잘 가르지 못한다(메모 §12-2).
  - 그래서 동의어 병합과 질문 tag 맞추기에서는 tag를 이름 대신 정의문이나 그 tag가 붙은 note들의 평균으로 표현하자는 의견이다.
  - 다만 tag를 고를 때 가까운 tag를 보여주는 용도로는 이름만 쓴 것이 가장 잘 맞았다(실험 §11). 용도마다 맞는 표현이 다를 수 있다.
  - 어느 경우든 embedding은 후보를 뽑는 데까지만 쓰고, 판정은 LLM에게 맡긴다.
- **tag와 embedding은 역할을 나눈다.** tag는 "어느 범위에서 찾을까", embedding은 "그 안에서 무엇이 가장 맞나"를 맡는다.

## 6. 그래서 어떻게 쓰이나

### 6-1. 다른 사람의 note로 답하기

1. 질문에도 등록된 tag와 topic을 붙인다. 등록된 tag는 목록 안에서만 고른다.
2. **후보를 고른다.** 공개된 note 가운데, 질문과 같은 등록된 tag가 있거나 질문 topic 주변의 topic이 붙은 note다. tag가 아직 안 붙은 note도 넣는다.
3. 후보가 20개보다 적으면 tag 필터를 버리고 embedding만으로 찾는다(폴백).
4. 질문에 고유명사가 있으면, 그 entity가 붙은 note를 후보에 넣고 점수를 더한다.
5. **embedding으로 줄 세운다.**
6. 상위 8개를 bourbon-agent에 넘긴다. ami가 답할지, 사람만 추천할지, 없다고 할지를 정한다.

**답할 수 있는지를 ami가 정하는 이유:** discovery가 "이 note로 답할 수 있다"고 따로 판정하면, 그 판정과 실제 답 사이에 어긋남이 생긴다. note를 읽고 답을 만드는 쪽이 그 자리에서 정하면 그 어긋남이 없다(메모 §9-2).

### 6-2. shout할 사람 고르기

**무엇을 기준으로 고르나.** shout는 "이미 쓴 note로 답할 수 있나"가 아니라 **"이 사람이 답해 줄 수 있을까, 관심 있을까"**로 고른다. 사람은 쓴 것보다 많이 알기 때문이다. 그래서 note 하나가 아니라 그 사람의 note와 tag 전체를 본다(메모 §10-2).

1. **사람마다 점수를 매긴다.** 두 가지를 각각 표준화해서 더한다.
   - **tag 프로필 점수:** 질문 tag가 그 사람의 note에 얼마나 붙어 있나
   - **note 유사도:** 질문과 가장 가까운 그 사람의 note 3개와 얼마나 가까운가
2. 상위 20명을 뽑는다.
3. **LLM 재순위:** LLM이 20명 각자의 tag와 note 제목, 질문과 가까운 note 본문 3개를 읽고 다시 줄 세운다. 2026-10-27에 채택한 것은 B1(`gemini-3.5-flash` low)이고, 다시 볼지 정하는 중이다(§8).
4. **shout 범위로 나눈다.** 질문의 등록된 tag 넓이로 "작게 / 보통 / 크게"를 만든다(§4-3). 0명인 단계는 보여주지 않는다.
5. **"왜 이 사람인지" 설명을 붙인다.** 겹치는 tag(한국어 표시 이름)와 가장 가까운 note 제목으로, LLM 없이 만든다. 예: "위스키·셰리 캐스크 note를 쓰셔서". 상호명·지명은 드러내지 않는다.

여기에 **사람 신호**도 두자는 의견이다. 아직 재지 않았다(메모 §11-2, §12-1).
- shout 응답 이력: 받았는지, 답했는지, 무시하거나 거절했는지
- 탐색 자리: 이력이 없는 사람에게 돌아가는 자리. 처음에 뽑힌 사람만 계속 뽑히지 않게 한다
- 한 사람이 받는 shout의 상한
- 대화 이력 목록은 같은 단계 안의 가산으로만 쓴다

## 7. 왜 이렇게 설계하나 — 실험이 뒷받침하는 것

### 7-1. 실험은 어떻게 했나

- **합성 데이터다.** 유저 100명이 각자 한국어 한 문단짜리 note 10개를 썼다. 모두 1,000개, 15개 분야다. 답하기용 질문은 400개(답이 있는 것 337개), shout용 질문은 95개다.
- **유저마다 "note로 쓰지 않은 경험"을 따로 두었다.** 고르는 쪽은 공개된 note와 tag만 본다. 정답은 쓰지 않은 경험까지 아는 판정 모델이 정한다. note에 없는 경험을 가진 사람을 찾을 수 있는지 보기 위해서다.
- **정답은 LLM 판정 모델이 붙였다.** 답하기는 `gpt-5.5`, shout는 `gemini-3.1-pro-preview`다. shout 판정 모델은 2026-10-29에 바꿨다. 이유는 §7-3에 있다.
- **비교 기준은 실행 전에 적었다(실험 §7 이후).** 결과를 보고 기준을 고르지 않으려는 것이다. 차이의 불확실성은 질문 단위로 다시 뽑아(bootstrap) 95% 신뢰구간으로 냈다.

**지표 읽는 법**
- 답하기의 **hit@5**: 상위 5개 note 안에 정답 note가 하나라도 있는 질문의 비율이다. **recall@10**은 정답 note 가운데 상위 10개 안에 든 비율이다.
- shout의 **p@5**: 고른 상위 5명 중 맞는 사람의 비율이다. **hit@5**는 상위 5명 안에 맞는 사람이 하나라도 있는 질문의 비율이다.
- shout에서 "맞는 사람"은 두 가지로 본다.
  - **관련 경험 + 관심:** 직접은 아니어도 들어 볼 만한 관련 경험이 있고, 그 주제에 관심이 있는 사람
  - **직접 경험자:** 그 일을 직접 겪은 사람

### 7-2. 설계 방향과 그 근거

| 설계 방향 | 근거 |
|---|---|
| **tag는 LLM이 자유롭게 만들지 않고, 등록된 목록에서 고른다** | 자유 생성은 tag가 1,852종이고 66%가 한 번만 쓰였다. 목록에서 고르면 415종, 24%다. tag 필터가 놓친 정답 note는 8.6%에서 1.2%로 줄었다(실험 §1) |
| **tag는 필터로만 쓰고, note 순위는 embedding이 매긴다** | tag 필터 + embedding은 embedding만 쓸 때와 거의 같은 정확도(hit@5 0.98 대 0.99)로 후보를 1/10로 줄였다. tag만으로 순위를 매기면 hit@5가 0.75로 떨어진다(실험 §2) |
| **키워드 검색(BM25)을 늘 섞지 않는다** | 모호한 질문에서 BM25를 섞으면 recall@10이 0.81에서 0.64로 떨어졌다(실험 §2). 고유명사는 entity로 다루고, 질문에 있을 때만 쓴다 |
| **답할지는 ami가 판단한다** | 상위 8개 note를 주고 답하게 했더니, 답이 없는 질문에 답을 지어낸 경우가 0건이었다. 인용 정확도는 거의 1.0이다(실험 §4) |
| **topic 카탈로그는 주축이 아니라 보완이다** | topic을 주축으로 tag를 붙이면 shout 단계가 거칠어지고 직접 경험자 찾기가 떨어졌다(실험 §8, §10). 등록된 tag를 주축으로 두고 topic으로 검색 필터만 보완하면 근소하게 나았다(실험 §9) |
| **사람 고르기는 tag + note 유사도 결합** | 상위 5명 중 관련 경험 + 관심인 사람은 무작위로 고르면 7%, 결합 방식은 약 40%다(실험 §6, §17) |
| **LLM 재순위를 더한다** | note 본문을 함께 읽히는 재순위(B1)는 그 비율을 통계적으로 올렸다(+0.042, 실험 §7, §17) |
| **shout 범위는 tag 넓이로 나눈다** | 단계별 인원이 작게 2명 / 보통 11명 / 크게 24명(중간값)으로 나뉜다. 관련 경험이 있는 사람의 비율(관심 여부는 따지지 않음)은 0.46 / 0.42 / 0.31로, 좁을수록 정확하다(실험 §8, §17) |
| **고유명사는 entity로 따로 둔다** | 사는 곳이 tag로 새는 것을 프롬프트로 막지 못했다(§4-4). 이름 tag를 빼도 답하기 품질은 그대로였다(실험 §14) |

표에 다 담지 못한 단서:
- **답의 일반론:** 모호한 질문과 여러 사람의 note가 필요한 질문에서는 답의 13~19%가 note에 없는 일반론을 덧붙였다. bourbon-agent에 요구사항으로 전달한다(실험 §4).
- **topic 주축의 수치:** topic 주축에서는 재순위 전 직접 경험자 hit@5가 −0.105였다. LLM 재순위까지 거쳐도 "나쁘지 않다"를 보이지 못했다(실험 §8, §10).
- **사람 고르기 방식 비교:** 결합 방식은 tag만, embedding만 쓰는 방식보다 대체로 낫거나 비슷했다(실험 §6, §17).
- **"작게" 단계:** 자주 0명이라 숨겨야 한다.
- **이름 tag를 뺐을 때의 shout:** 직접 경험자 hit@5가 −0.042로, 질문 95개로는 가를 수 없었다. "작게"가 빈 질문은 43%에서 58%로 늘었다(실험 §14). entity의 효과는 실험 계획 E에서 잴 계획이다. E를 돌릴지는 아직 정하지 않았다.

### 7-3. 확인한 것과 아직 모르는 것

**확인한 것**
- 한 문단 note만으로 다른 사람의 질문에 답할 재료가 된다(실험 §5).
- 공개된 note와 tag만으로 shout할 사람을 무작위보다 훨씬 잘 고른다(실험 §6, §17).
- note가 적은 유저가 많아도 전체 품질은 미리 정한 경고선(0.10) 안에서 버틴다(실험 §12). 다만 이 경고선은 처음 판정의 척도에서 정한 것이라, 지금 기준 라벨에서는 비율로 두 배쯤 느슨하다(실험 한계).
- 판정 모델을 다른 계열로 바꿔도 "직접 겪었다" 판정은 잘 맞는다. 두 판정이 우연 이상으로 일치하는 정도(kappa, 1이 완전 일치)가 0.81이다(실험 §13).

**조심해서 읽을 것**
- **"관련 경험이 있다"는 판정 모델마다 크게 다르다.**
  - 사람 대신 Claude 모델 둘(rater)이 새 정의로 라벨을 붙여 비교했다. 처음 쓴 판정(`gpt-5.5`)은 그 라벨보다 "관련 경험"을 두 배 넘게 후하게 봤다(양성 0.82 대 0.36~0.40).
  - 같은 비교에서 Gemini 판정이 근소하게 가장 잘 맞아서 기준 라벨로 바꿨다(실험 §15).
  - 기준 라벨을 고른 근거가 사람이 아니라 Claude 모델이라 약한 근거다.
  - 경계에 있는 사람의 라벨은 함께 판정된 사람들에 따라 조금 움직였다(실험 §17).
- **이 문서의 shout 비율은 모두 바꾼 기준 라벨의 값이다.** 메모 §12-1과 실험 §6~§8에 있는 0.84, 0.83 / 0.77 / 0.67은 처음 판정(`gpt-5.5`) 값이다(실험 §17).
- **"직접 겪은 사람"을 찾기는 아직 어렵다.**
  - 직접 겪은 사람이 상위 5명 안에 하나라도 드는 질문은 절반이 안 된다(0.45~0.48, 실험 §17).
  - 다만 분야 근처의 질문(near) 28개 중 23개는 직접 겪은 사람이 아예 없었다(실험 §6). 관심 분야 밖의 경험은 note에 드러나지 않는다.
- **note가 적은 사람은 상위 5명에서 밀린다.** note 1개인 직접 경험자는 13%만 상위 5명에 든다. note 10개면 74%다(실험 §12, 처음 판정 기준. 직접 경험 라벨은 두 판정이 잘 맞는다).

**아직 재지 않은 것**
- note 1만 개 이상의 규모
- 실제 사람의 응답률과 피로도(dev에서만 잴 수 있다)
- 옛 note와 새 note의 내용이 다를 때
- entity의 효과와 잘못 뽑히는 비율(실험 계획 E, entity 실험)
- 맞는 topic이 후보 안에 들어오는지(실험 계획 F, topic 후보 실험)

## 8. 아직 정하지 않은 것

| 무엇 | 지금 상태 |
|---|---|
| shout 재순위 모델 | 아래 표를 본다 |
| tag 목록이 커질 때 | 아래 표를 본다 |
| system tag 방식을 메모 §12-1대로 할지 | 결정 항목 2. 오너가 정한다 |
| tag·entity·질문 tag를 discovery가 맡을지 | 결정 항목 4에 넣을지 정한다(메모 §12-4) |
| note 원본을 어느 서비스가 가질지 | 정하지 않았다 |
| 실험 계획 E·F를 돌릴지 | 정하지 않았다 |
| 등록된 tag와 entity의 경계 | 상품·브랜드 이름(`glendronach`, `starbucks`)을 tag에서도 뺄지 실험 계획 E에서 본다 |
| note가 적은 사람 | 탐색 자리를 둘지, 점수를 보정할지 정한다 |
| 이벤트에 본문을 담을지 | key만 담고 본문은 조회하는 쪽을 권한다(메모 §5-2) |

**shout 재순위 모델**
- **보호 기준:** 재순위 뒤 직접 경험자 hit@5가 떨어지는 폭의 95% 신뢰구간 하한이 −0.05 이상이어야 한다.
- **B1(flash low):** 기준 라벨로는 이 보호 기준을 넘지 못했다(하한 −0.084).
- **B3(flash medium)와 B4(pro):** 넘었지만 유리하게 나왔을 수 있다.
  - B4는 판정 모델과 같은 모델이고, B3도 같은 계열이다.
  - B3의 효과는 기준 라벨에서 거의 두 배가 됐다.
  - 기준 라벨로 처음부터 골랐다면 B1이 아니라 B2를 골랐을 것이다.
- **비용과 지연:** B1이 가장 작다(실험 §7, §17).

**tag 목록이 커질 때**
- 지금은 tag를 고를 때 목록 전체(약 400개)를 프롬프트에 넣는다.
- 가까운 50개만 보여주면 새 tag가 두 배로 늘었다.
- 자유 제안 후 맞추기와 넓은 tag 함께 보여주기도 목록을 1.4~1.5배로 부풀렸다.
- 다음 후보는 보여주는 개수 k를 키우는 것이다(실험 §11, §16).

## 9. 용어

| 용어 | 뜻 |
|---|---|
| 등록된 tag | 지금까지 쓰인 tag 목록에 있는 tag. 실험 코드의 registry tag다 |
| 넓이 | 등록된 tag가 얼마나 넓은 주제인지(specific / mid / broad). 처음 등록할 때 정해 고정한다 |
| 카탈로그 topic | bourbon-topic-api가 관리하는 계층형 주제 목록의 항목 |
| entity | note에 나온 고유명사. 정규형, 종류, 별칭, 역할(주제 / 언급)을 둔다 |
| embedding | 글을 숫자 벡터로 바꾼 것. 뜻이 가까울수록 벡터가 가깝다 |
| shout 범위 | shout를 보낼 후보의 크기. 작게 / 보통 / 크게 |
| 재순위 | 1차로 뽑은 후보를 LLM이 다시 읽고 줄 세우는 것. B1~B4는 실험에서 비교한 재순위 변형이다 |
| 판정 모델 | 실험에서 정답을 붙인 LLM |
| 기준 라벨 | 실험에서 "정답"으로 쓰는 판정 결과. shout는 2026-10-29부터 `gemini-3.1-pro-preview`의 판정이다 |
| rater | 판정 모델들을 평가하려고 라벨을 붙인 쪽. 사람 대신 Claude 모델 둘이 맡았다 |
| kappa | 두 판정이 우연 이상으로 일치하는 정도. 1이면 완전 일치 |
| 관련 경험 + 관심 | shout 지표. 직접은 아니어도 들어 볼 만한 관련 경험이 있고, 그 주제에 관심이 있는 사람 |
| 직접 경험자 | 질문의 주제를 직접 겪은 사람 |
