## A. tag 두 층: topic tag + registry tag

### A-1. 비교하는 방식

| 방식 | note에 붙는 tag | 넓히는 단계 |
|---|---|---|
| R (이전 실험 그대로) | registry tag 3~6개, LLM이 정한 넓이 포함 | 작게: specific / 보통: +mid / 크게: +broad |
| T | topic tag 1~3개 | 작게: 같은 topic / 보통: 부모 topic 아래 / 크게: 조부모 topic 아래 |
| TR | topic tag 1~3개 + registry tag 0~3개 | 작게: 같은 registry tag / 보통: 같은 topic 아래 / 크게: 부모 topic 아래 |

- "X 아래"는 X와 그 하위 topic 전체다. 질문의 topic과 note의 topic이 이 관계면 매칭으로 본다.
- R은 이전 결과를 다시 쓴다. 새로 돌리는 것은 T와 TR이다. T는 TR에서 registry tag를 빼고 계산하면 되므로 tag는 한 번만 붙인다.

### A-2. topic 목록

- agent-discovery-api의 `data/catalog_dist/catalog.json`을 쓴다. bourbon-topic-api가 2026-09-22에 만든 것이고 Wikidata 덤프 `20260802` 기반이다.
- active topic 3,161개만 쓴다. merged 13개는 뺀다. edge는 `[자식, 부모]` 3,120개다.
- **실험 데이터와 독립적이다.** note는 15개 분야로 만들었지만 카탈로그는 그 분야를 모르고 만들어졌다. 데이터를 만든 15개 분야를 topic 목록으로 쓰면 정답을 미리 알려준 셈이 되어 결과가 부풀려진다. 그래서 쓰지 않는다.
- 사전 확인: 이전 registry tag 415종 중 56종이 카탈로그 이름·별칭과 문자열로 같다. 사용 횟수로는 43%다(임시 메모 §11-1).

### A-3. tag 붙이기

note마다:
1. **topic 후보 50개를 뽑는다.** topic마다 영어 이름, 한국어 이름, 설명, 별칭으로 문장을 만들어 document로 embedding해 둔다. note 본문은 query로 embedding해서 가장 가까운 50개를 고른다. 카탈로그 전체를 프롬프트에 넣으면 note마다 2만 토큰 가까이 들어서 이렇게 한다.
2. **LLM이 topic tag 1~3개를 고른다.** 후보 50개 중에서만 고른다.
3. **LLM이 registry tag 0~3개를 붙인다.**
   - 고른 topic으로 담기지 않는 구체적인 이름이나 세부 주제일 때만 붙인다.
   - 등록된 registry tag 목록을 보여주고, 맞는 것이 있으면 그대로 다시 쓴다. 없을 때만 새로 만든다.
   - 새로 만들 때는 후보 50개 중에서 부모 topic을 하나 지정한다. 맞는 것이 없으면 비운다.
4. **장소 규칙:** note의 주제가 장소일 때만 장소를 tag로 붙인다. 글쓴이가 사는 곳은 붙이지 않는다.

- 2와 3은 한 번의 호출로 한다. 모델은 이전 실험과 같은 `gemini-3.5-flash`, low effort다.
- registry는 이전 실험처럼 25개씩 묶어 근사한다. 한 묶음은 그 묶음이 시작될 때의 목록을 본다.
- **질문 tag:** 질문도 같은 방법으로 topic 후보 50개를 뽑고 topic tag를 고른다. registry tag는 등록된 목록 안에서만 고른다. 모델은 이전 실험과 같은 `gemini-3.5-flash-lite`, low effort다.
- note와 질문의 tag 출력에 고른 이유는 받지 않는다. 비용만 늘고 지표에 쓰이지 않는다.

### A-4. 지표

**tag 품질**

| 지표 | 무엇을 보나 |
|---|---|
| note당 topic tag 수 분포 | 1~3개 안에서 고르게 쓰는가, 늘 3개를 채우는가 |
| registry tag 종류 수, 한 번만 쓰인 비율, 표기 중복 쌍 | R(415종, 24%, 1쌍)보다 줄었는가 |
| 부모 topic 없는 registry tag 비율 | topic 목록에 빈 곳이 얼마나 있는가. 어떤 분야에 몰리는가 |
| topic이 있는데 registry tag를 만든 비율 | "topic 먼저" 규칙이 지켜지는가. 새 registry tag의 이름이 카탈로그 이름·별칭과 같거나 embedding이 아주 가까운 topic이 있으면 위반으로 센다 |
| 장소 tag 비율 | R에서 153번 붙은 지역 tag가 사라졌는가 |

**검색** (이전 실험의 질문 400개, 정답 라벨 재사용)

| 지표 | R의 값 |
|---|---|
| tag 필터가 놓친 정답 note 비율 | 1.2% |
| tag 필터 → embedding + 폴백의 hit@5, recall@10 | 0.982, 0.866 |
| 필터 후 후보 수 중간값 | 106 |

**shout 범위와 대상 선정** (이전 실험의 shout 질문 95개, 판정 라벨 재사용)

| 지표 | R의 값 |
|---|---|
| 단계별 인원 중간값 (작게/보통/크게) | 2 / 11 / 24 |
| "작게"가 0명인 질문 비율 | 그룹별로 다시 계산해 함께 보인다 |
| 단계별 관련 경험자 비율 | 0.83 / 0.77 / 0.69 |
| tag 프로필로 고른 대상의 관련 경험 + 관심 p@5, 직접 경험자 hit@5·hit@10 | 0.81, 0.45, 0.60 |
| tag 프로필 + embedding 결합 | 0.84, 0.54, 0.63 |

- tag 프로필은 이전과 같은 방식(희소도 × 사용 횟수)으로 만든다. TR에서는 topic tag에 조상 topic까지 펼쳐 넣고, 넓이 가중 대신 계층 깊이를 쓴다.

### A-5. 판정 추가

- 검색: 새로 상위 10개 안에 들어왔는데 이전 판정에 없던 note만 `gpt-5.5`로 판정한다.
- shout: 단계 구성원과 선정 상위 20명 중 이전 판정에 없던 사람만 판정한다. 판정 방식은 실험 문서 §6과 같다.
- 판정에 없던 것을 "답할 수 없음"으로 세지 않고 판정해서 채운다. 새 방식이 판정 후보에 없던 사람을 찾았을 때 불리해지지 않게 하기 위해서다.

### A-6. 판단 기준

TR이 아래를 만족하면 두 층 구조를 기본안으로 올린다.
- tag 필터가 놓친 정답 비율이 R(1.2%)보다 높지 않다.
- "작게" 0명 비율이 R보다 낮다.
- shout 대상 선정 지표가 R보다 나쁘지 않다.
- 부모 topic 없는 registry tag와 "topic 먼저" 위반이 둘 다 낮다. 수치 기준은 결과를 보고 정한다. 높으면 tag 붙이기 프롬프트나 후보 수(50개)를 먼저 고친다.

### A-7. 이번에 하지 않는 것

- registry tag 동의어 병합 장치: 결과에서 표기 중복이 문제로 남으면 다음에 붙인다.
- registry tag를 topic으로 올리는 절차: 실제 사용량이 있어야 의미가 있다.
- 유저 태그, "물어봐도 되는 분야" 표시(임시 메모 §11-4).

## B. LLM 재순위 재확인

### B-1. 개선 여지

판정 라벨로 tag + embedding 결합의 상위 20명을 완벽하게 다시 줄 세웠을 때의 상한이다(2026-10-27 계산).

| | 결합 | 이전 재순위 | 상한 |
|---|---|---|---|
| 관련 경험 + 관심 p@5 (95문항) | 0.84 | 0.87 | 0.98 |
| 직접 경험자 hit@5 (95문항) | 0.54 | 0.51 | 0.71 |
| 직접 경험자 hit@5 (관심 분야 밖, 19문항) | 0.32 | 0.37 | 0.74 |
| 직접 경험자 hit@5 (관심 분야 안, 33문항) | 0.79 | 0.67 | 1.00 |

- 직접 경험자 hit@5의 상한이 0.71인 것은 직접 경험자가 상위 20명 안에 아예 없는 질문이 있어서다. near 질문은 대부분 직접 경험자가 없다.
- 재순위가 얻을 수 있는 몫은 "결합"과 "상한" 사이다. 이전 재순위는 관련 경험 + 관심 p@5에서 그 몫의 약 20%를 얻었고, 직접 경험자 hit@5에서는 오히려 잃었다.

### B-2. 바꿔 볼 것

이전 설정: 입력은 tag 구성과 note 제목, 모델은 `gemini-3.5-flash` low effort, 점수는 0~3 하나, 깊이 20.

한 번에 하나씩 바꾼다. 모든 조합을 돌리지 않는다.

| 변형 | 입력 | 모델 | 점수 |
|---|---|---|---|
| B0 | 이전과 같음 | flash low | 0~3 하나 |
| B1 | + 질문에 가장 가까운 note 3개의 본문 | flash low | 0~3 하나 |
| B2 | B1과 같음 | flash low | "답할 수 있음" 0~10, "관심 있음" 0~10을 따로 |
| B3 | B1·B2 중 나은 것 | flash medium | 그 점수 방식 |
| B4 | B1·B2 중 나은 것 | `gemini-3.1-pro-preview` | 그 점수 방식 |

- B0은 이전 결과를 캐시에서 그대로 다시 읽는다. 호출이 들지 않는다.
- B2의 순서는 "답할 수 있음"을 먼저, 동점이면 "관심 있음"으로 정한다. 직접 경험자 찾기가 목적이기 때문이다.
- **판정 모델(`gpt-5.5`)과 같은 계열은 쓰지 않는다.** 판정과 취향이 같아서 점수가 부풀려진다.
- 깊이는 20으로 고정한다. 상위 20명은 모두 이전 판정 후보 안에 있어서 **추가 판정이 필요 없다.**

### B-3. 지표와 판단

- 지표: 관련 경험 + 관심 p@5·p@10, 직접 경험자 hit@5·hit@10. 그룹별(관심 분야 안/밖, broad, near)로 본다.
- 개선 여지 중 얻은 몫: (변형 − 결합) / (상한 − 결합)
- **잡음 확인:** 질문이 95개뿐이라, 결합 대비 차이를 질문 단위로 짝지어 bootstrap 신뢰구간을 낸다.
- 호출당 입력·출력 토큰과 지연 시간을 함께 적는다. shout 한 건마다 한 번 호출하는 비용이다.
- **판단:** 관련 경험 + 관심 p@5나 직접 경험자 hit@5의 개선이 신뢰구간상 0보다 크고, 호출 비용과 지연이 받아들일 만하면 재순위를 쓴다. 아니면 뺀다.
- "왜 이 사람인지" 설명은 이 실험과 별개다. 겹치는 tag와 가장 가까운 note 제목으로 만든다(임시 메모 §11-3). 재순위를 쓰게 되면 그 출력에 이유를 함께 받는 것도 그때 본다.
