## 0. 요약

- 유저의 에이전트 이름은 **ami**가 될 것 같다.
- 유저가 ami와 대화하며 어떤 주제에 대한 정보가 쌓이면 **ami의 note**가 만들어진다. 요약·정리되어 publish되는, SNS의 post 같은 것이다.
- note는 세 가지에 쓰인다.
  - 유저의 프로필 페이지(**portal**)를 꾸미는 재료
  - 다른 유저가 내 ami와 대화할 때 ami가 쓰는 재료
  - 추천의 재료
- **기존 topic은 없어질 것 같다.** note에 자연어 태그가 붙는다. 시스템이 붙이는 것과 유저가 붙이는 것이 있다. topic별 성숙도·점수도 함께 사라진다.
  - 2026-10-27: topic별 점수와 topic 단위 검색은 사라지지만, **topic 카탈로그와 계층은 system tag의 한 종류(topic tag)로 다시 쓰는 쪽을 검토 중**이다(§11-1).
  - 2026-10-28: 실험 뒤 검토 의견은 등록된 tag 주축, 카탈로그 topic 보완이다(오너 응답 전). 고유명사를 entity로 따로 뽑는 것과 system tag를 discovery가 붙이고 관리하는 것은 오너 의견에 검토 의견이 동의했다(§12, 결정 아님).
  - 2026-10-29: 등록된 tag는 영어 키 + 고정된 한국어 표시 이름, entity 정규형은 원래 언어 표기 + 다른 표기는 별칭이라는 검토 의견에 오너가 동의했다(§12-5, 결정 아님).
- 추천은 세 단계다.
  1. 다른 유저들의 note로 **답을 직접 만들고**, 답에 쓰인 note의 유저와 대화해 보라고 함께 추천한다.
  2. 답은 못 만들지만 대화해 볼 만한 유저를 **답 없이** 추천한다.
  3. 그것도 어려우면 **shout**로 답할 수 있을 것 같은 유저에게 질문을 보내고, 받은 유저가 답한다.
- note를 어디에 어떻게 저장할지는 정해진 바가 없다.

discovery 쪽 판단: 지금까지 논의한 것과 잘 맞고, 구조는 오히려 단순해진다. 다만 지금 discovery 코드의 큰 부분이 topic 전제라서 확정되면 재설계 규모가 크다.

## 1. 용어

| 용어 | 뜻 |
|---|---|
| ami | 유저의 에이전트 시스템 이름(가칭). |
| ami의 note (이하 note) | ami와의 대화에서 만들어져, 유저가 확인한 뒤 publish되는 요약·정리 글. post에 가깝다. |
| portal | 유저의 프로필 페이지. 내부 임시 이름이다. note를 재료로 콜라주 등 어떤 형태로든 꾸며지고, 일부 note가 직접 보인다. |
| system tag | 시스템이 note에 자동으로 붙이는 태그. 지금의 topic 역할을 맡는다. 한 note에 여러 개가 붙는다(§8-1). 유저에게 보일 수도 안 보일 수도 있다. §11-1부터는 topic tag와 registry tag 두 종류로 나눈다. |
| topic tag | topic 카탈로그에서 골라 붙이는 system tag. 한 note에 여러 개가 붙고, 카탈로그의 계층을 따른다(§11-1). |
| registry tag | 카탈로그가 담지 못하는 구체적인 이름이나 세부 주제에 붙이는 system tag. 지금까지 쓰인 tag 목록(registry)에서 먼저 고르고, 없을 때만 새로 만든다. 가능하면 부모 topic에 연결한다(§11-1). 본문의 "등록된 tag"도 이것이다. |
| entity | note에 나오는 고유명사(지명, 상품명, 상호명, 작품명). system tag와 따로 뽑고, 정규형·종류·별칭·역할(주제/언급)을 둔다. 정규형은 그 대상의 원래 언어 표기다(국내 대상은 한국어, 해외 대상은 원어. §12-3, §12-5). |
| 유저 태그 | 유저가 직접 입력한 자유 형식 태그. 첫 제품에는 없다고 보고, 나중에 추가할 수 있게 열어 둔다(§8-1). |
| 대화 이력 목록 | 내 portal에 와서 내 ami와 대화한 유저 목록, 그리고 내가 다른 유저의 portal에 가서 대화한 유저 목록. 첫 제품에서 친구 관계를 대신한다(§8-2). |
| shout 범위 | shout를 얼마나 넓은 후보에게 보낼지. 확성기 소리 크기처럼 유저가 조절한다(§8-6). |
| 명시적 shout | 추천 단계를 거치지 않고 유저가 직접 던지는 shout(§9-1). |
| 결과 묶음 | 질문 하나에 대한 note 검색 결과. 근거 note, owner 단위 사람 후보, shout 범위별 후보를 함께 담는다(§9-1). |
| 답 생성 추천 | 추천 1단계. 다른 유저들의 note로 답을 만들고 출처 유저를 함께 추천한다. knowledge 문서 열린 항목 33(answer mode)이 주 경로가 된 것이다. |

## 2. 지금 구조와의 대응

### 2-1. 하나로 합쳐지는 것

지금은 비슷한 일을 하는 것이 둘 있다.
- **topic**: 공개 범위의 단위이자 추천의 근거.
- **lived-knowledge 기록**: 답의 재료.

note는 이 둘을 하나로 합친다. 유저가 보는 것, ami가 대화에 쓰는 것, 추천에 쓰는 것이 모두 같은 note다.

"공개된 것만 추천 근거로 쓴다"는 지금까지의 원칙은 더 자연스러워진다. knowledge 문서 열린 항목 33에서 전제 조건으로 남겨 둔 동의 문제(남의 지식으로 답을 만들어도 되는가)도 쉬워진다. 유저가 확인하고 publish한 것이 곧 동의이기 때문이다.

### 2-2. 추천 세 단계의 대응

| 새 흐름 | 지금 문서에서 대응하는 것 |
|---|---|
| 1. 답을 만들고 출처 유저를 추천 | knowledge 문서 열린 항목 33(answer mode) → 주 경로로 승격 |
| 2. 답 없이 대화해 볼 유저를 추천 | knowledge 추천(타입 ④) |
| 3. shout | shout 문서 |

knowledge 문서의 파이프라인 뼈대(검색 → judge가 covers 판정 → 실패하면 다음 단계)는 재사용할 수 있다. 바뀌는 것은 검색 단위가 note라는 점이다.

### 2-3. topic이 사라지면 대체해야 하는 것

| topic이 하던 일 | 대체 후보 |
|---|---|
| 검색 대상(`visible_topic_rows`, 타입 ① 매칭, R69 하위 topic 매칭) | system tag 일치 + note 본문 임베딩 검색 + 키워드 검색(§4) → 2026-10-28: 키워드 검색 대신 entity 일치를 검토한다(§12-3) |
| 공개 범위(visibility가 topic을 따름) | **note 단위 공개 범위.** 공개/비공개 두 가지, 기본은 공개(§8-3) |
| 품질 신호(`topic_score`, `topic_maturity`) | note 단위 신호. 몇 번의 대화에서 나왔는지, 최근성, 유저가 직접 손봤는지, 답에 쓰여 도움이 됐다는 피드백 등 |
| 카탈로그 계층(shout 차수 확장, 상위·형제 topic) | 계층 대신 태그 간 유사도, 같은 note에 함께 붙는 빈도(동시 출현), 또는 유사도 임계값을 단계적으로 낮추기 |
| 추천 이유 문구("위스키를 공개 관심사로 두셔서") | "이 note를 쓰셔서" 또는 태그. 오히려 더 구체적이 된다 |

### 2-4. 그대로 쓸 수 있는 것과 쓸모없어지는 것

- **그대로 쓸 수 있다** (topic과 무관):
  - `interactions` / `room_turns`
  - `popularity`
  - `attributions`
  - `agents`의 활동 시각
  - shout 원장(shout 문서 §8)
- **쓸모없어진다**: `visible_topic_rows`, `catalog_edges`, topic 기반 CF, 그리고 그 위에 쌓은 R 결정 상당수.
- **첫 제품에서는 쓰지 않는다**: `friends`. 첫 제품에 친구 관계가 없다. 나중에 다시 들어올 수 있다(§8-2).

## 3. 열린 질문과 지금까지의 의견

각 항목에서 "오너 의견"은 2026-10-12 오너의 개인 의견이고 결정이 아니다. "검토 의견"은 discovery 쪽 의견이다.

### 3-1. note의 단위와 생성 시점

- **오너 의견**
  - 언제 만들지는 아직 말할 수 없다.
  - 같은 주제로 대화가 더 쌓이면 기존 note를 갱신하기보다 **새 note를 만드는 형태**일 것 같다. 새 post가 올라가는 느낌이다.
  - 새 note를 만들 때 기존 note를 참고해서 쓸 수는 있을 것이다.
- **검토 의견**
  - 같은 사람의 note가 여러 개 검색된다. 사람을 추천할 때는 **owner 단위로 묶어야** 한 사람이 목록을 다 차지하지 않는다.
  - 옛 note와 새 note가 다를 수 있다(예: 예전엔 피트를 싫어했는데 지금은 좋아함). 답을 만들 때 **최근 note를 우선하는 기준**이 필요하다.
  - post라도 수정·삭제는 일어난다. 수정·삭제 이벤트는 여전히 필요하다(§5).
  - 기록이 계속 쌓이는 문제(knowledge 문서 열린 항목 32)는 다시 생긴다. 다만 단위가 문장보다 훨씬 굵어서 부담은 작다.

### 3-2. publish 전 유저 확인

- **오너 의견**: 유저 확인을 거친다.
- **검토 의견**
  - 동의 문제가 깔끔해진다.
  - 확인 화면에서 이 note가 portal에 보일 뿐 아니라 **다른 사람의 질문에 답하는 재료로도 쓰인다**는 것을 알려야 한다. 그래야 인용됐을 때 유저가 놀라지 않는다.
  - 유저가 거절한 초안은 publish되지 않으므로 discovery로는 아예 오지 않는다.

### 3-3. 보여주는 용도와 답하는 용도의 충돌

- **검토 의견**
  - portal에 쓰는 note는 짧고 보기 좋아야 한다.
  - 답의 재료로 쓰는 note는 구체적이어야 한다. knowledge 문서 열린 항목 33에서 이미 "요약은 얇다"고 지적했다.
  - 하나의 note에 **표시용 레이어와 본문 레이어**를 같이 두는 구조를 고려할 만하다.
- **오너 의견**: 좋은 지적이라 참고하겠다.

### 3-4. 태그의 역할

- **오너 의견**
  - system tag를 지금의 topic과 같은 역할로 쓰고, 유저 태그도 있다고 하면, 이걸로 검색해도 좋지 않을까.
  - system tag는 유저에게 보일 수도 안 보일 수도 있다.
  - 정규화가 꼭 필요한지는 모르겠다. 유저가 자유 입력한 것 자체에도 의미가 있고, UX상 결국 비슷한 태그를 쓰게 되지 않을까. 이상한 태그를 다는 건 유저의 몫이다.
- **검토 의견**: §4에 정리했다.

### 3-5. lived-knowledge 기록과의 관계

- **오너 의견**: note가 lived-knowledge를 대체하는 형태가 될 것 같다.
- **검토 의견**
  - 기록을 추출하던 파이프라인(knowledge 문서 §7)은 **note를 생성하는 쪽 일**이 된다. 소유 서비스가 바뀔 수도 있다.
  - discovery는 **인덱스·검색·순위**만 맡게 된다.
  - 기록에 있던 `kinds[]`(경험, 의견 등)는 note의 system tag나 메타데이터로 옮기면 된다.
  - 출처 표시는 문장 단위가 아니라 note 단위가 된다. 사람을 추천하는 데는 그 정도로 충분하다.
  - 이미 scaffold한 lived-knowledge repo와 knowledge 문서의 수집 부분은 확정되면 정리해야 한다.

### 3-6. 초기에 note가 없는 시기(cold start)

- **오너 의견**: 아직 모르겠다. 기획팀에서 더 자세한 기획이 필요하다.
- **검토 의견**
  - note가 쌓이기 전에는 추천 1·2단계가 거의 실패하고 shout 비중이 커진다.
  - shout 답이 답한 사람의 **note 초안**이 되는 구조라면, shout가 초기에 note를 채우는 경로가 될 수 있다. shout 문서 §7에서 답을 경험 기록으로 쌓는 것과 같은 논리다.

### 3-7. 저장 소유권

- **검토 의견(제안한 원칙)**
  - note 원본은 **한 서비스가 소유**한다(note 서비스든 bourbon-api든).
  - discovery는 지금 topic row를 미러링하듯 이벤트로 받아 **검색 인덱스(임베딩)와 공개 범위 사본**만 가진다.
  - → 2026-10-28: system tag, 등록된 tag 목록, entity는 discovery가 만들고 원본을 갖는 쪽을 검토한다. note 원본은 그대로 한 서비스가 갖는다(§12-4, 결정 아님).
  - 이렇게 하면 "discovery에는 공개된 것의 사본만 있다"는 지금의 경계가 그대로 유지된다.
- **오너 의견**: 이 원칙은 적당해 보인다.

## 4. 태그와 검색 (검토 의견)

### 4-1. 태그를 임베딩하면 약하다

짧은 태그 하나만 임베딩해서 검색하면 약하다.
- **문맥이 없다.** "피트"는 위스키의 피트, 길이 단위, 사람 이름일 수 있다.
- **길이가 맞지 않는다.** 질문은 문장이고 태그는 단어다. "셰리 캐스크인데 너무 달지 않은 거 추천해줘"와 태그 `셰리`의 유사도는 생각보다 낮고 순위도 불안정하다.
- **같은 범주끼리 뭉친다.** 단어 임베딩은 "위스키", "와인", "칵테일"을 서로 가깝게 둬서 구체적인 구분이 흐려진다.

태그를 **정확히 일치**시키거나 **키워드 검색**으로 쓰면 짧은 것은 문제가 되지 않는다. 오너 의견(태그로 검색)과는 이 방식으로 맞춰진다.

### 4-2. 정규화가 필요한 곳은 system tag다

- **system tag**
  - topic 역할을 하려면 같은 것에는 늘 같은 태그가 붙어야 한다.
  - LLM은 호출할 때마다 표기가 달라진다(`셰리 캐스크`, `셰리캐스크`, `Sherry cask`).
  - 그래서 LLM이 **지금까지 등록된 태그 목록에서 먼저 고르고**, 정말 없을 때만 새로 만들게 한다. 그러면 따로 정규화하지 않아도 만드는 순간 정규화된 상태가 된다.
- **유저 태그**
  - 오너 의견대로 자유 입력 자체에 의미가 있다.
  - 입력할 때 기존 태그를 **자동완성으로 제안**하면 UX만으로 표기가 모인다.
  - 이상한 태그는 그 유저 본인의 노출만 손해 본다.
  - 주의할 점: 유저 태그를 남의 질문 순위에 크게 반영하면, 인기 태그를 잔뜩 달아 노출을 노리는 유저가 생길 수 있다. **가산을 작게** 두는 편이 안전하다.

### 4-3. 검색 역할 나누기

| 무엇으로 | 역할 |
|---|---|
| system tag | 구조화된 일치. 지금의 topic 매칭을 대신한다 |
| 유저 태그 | 작은 가산, portal 표시 |
| note 본문 임베딩 | 의미 검색. 태그가 놓치는 것을 잡는다 |
| 키워드 검색(BM25 등) | 고유명사(증류소, 제품명) 일치. 임베딩과 함께 하이브리드로 쓴다 → 2026-10-28: 고유명사는 entity 일치로 바꾸자는 의견이다. BM25를 entity가 있는 질문의 보조로 둘지는 잰다(§12-3, 결정 아님) |

system tag에 계층이 없으면 "넓히기"(shout 차수 확장, R69 하위 topic 매칭)를 다른 방식으로 해야 한다. §2-3의 대체 후보 중에서 고른다.

## 5. note 사본을 discovery에 두는 방식 (검토 의견)

오너 제안: note는 다른 서비스가 임베딩 없이 저장한다. discovery는 이벤트를 받아 임베딩을 만들고 note의 key를 함께 저장해 추적한다.

이 방향이 좋다고 봤다. 지금 topic row를 다루는 방식과 같고, 이벤트 worker를 소비하는 쪽 repo에 두는 기존 관례와도 맞는다. 다만 아래가 필요하다.

### 5-1. 생성 말고도 받아야 할 이벤트

| 이벤트 | 받지 않으면 |
|---|---|
| 생성 | — |
| 수정 | 옛 내용으로 검색되고, 옛 내용이 답에 인용된다 |
| 삭제 | 유저가 지운 note가 남의 답에 계속 쓰인다. **개인정보 문제라 가장 중요하다** |
| 공개 범위 변경 | 비공개로 돌린 note가 계속 추천 근거로 쓰인다 |
| 탈퇴 | 지금 `departed_users`가 하는 일을 note에도 해야 한다 |

이벤트는 순서가 바뀌어 도착할 수 있다. 이벤트에 `version`(또는 `updated_at`)을 담고, 받는 쪽은 더 새로운 버전일 때만 반영한다.

### 5-2. 이벤트에 무엇을 담나

- **key만 담고 본문은 note 서비스에서 조회 (권장)**: 항상 최신 본문을 읽고, 원본이 한 곳에만 있다. note 서비스에 읽기 API가 필요하다.
- **이벤트에 본문까지 담기**: 조회 호출이 필요 없지만 이벤트 큐에 본문이 남는다.

어느 쪽이든 note 서비스의 읽기 API(단건 조회, 목록 조회)는 결국 필요하다. 임베딩 모델을 바꿀 때 전체를 다시 임베딩해야 하고, 누락분도 맞춰야 하기 때문이다.

### 5-3. discovery에 저장할 것

| 필드 | 이유 |
|---|---|
| `note_id`, `owner_user_id` | 추적, 출처 표시 |
| `version` | 순서 역전 방지 |
| `visibility` | 검색할 때 공개 범위 필터링 |
| `embedding`, `embedding_model` | 모델을 바꿀 때 다시 임베딩할 대상 찾기 |
| system tag, 유저 태그 | 일치·가산 |
| `embedded_at`, 상태(pending/done/failed) | 실패 추적 |

- **본문을 저장할지는 정해야 한다.**
  - 저장하지 않으면 원본이 한 곳에 있다는 점이 깔끔하게 지켜진다.
  - 키워드 검색을 하려면 검색용 텍스트가 discovery에 있어야 한다.
  - 저장한다면 검색 인덱스 용도로만 두고, 삭제 이벤트에 확실히 함께 지운다는 조건을 붙이는 것이 현실적이다.
- **저장소**: PostgreSQL + pgvector가 자연스럽다. 이미 PostgreSQL을 쓰고 있고, 공개 범위 필터와 벡터 검색을 한 쿼리로 할 수 있다.

### 5-4. 실패 처리

deferq에는 재시도와 DLQ가 없다. 임베딩 호출(e3llm)이 실패하면 그 이벤트는 사라진다. 그래서 두 가지를 둔다.
- 이벤트를 받으면 먼저 `pending` row를 쓰고, 임베딩은 그다음에 한다. 실패한 것은 worker loop가 재시도한다.
- 주기적으로 note 서비스 목록과 대조해 누락분을 채운다.

### 5-5. 답을 만들 때는 원본을 다시 확인

discovery의 사본은 늘 약간 늦다. 검색은 사본으로 하더라도, 답의 재료로 넘기기 직전에는 note 서비스에서 해당 key들을 다시 조회한다. 삭제됐거나 비공개로 바뀐 것은 빼고, 본문은 이때 최신으로 가져온다. 그러면 이벤트가 늦게 도착하는 사이에도 지운 note가 인용되지 않는다.

## 8. 2026-10-21 추가 논의

"오너 공유"는 기획 쪽에서 지금 이야기되고 있는 내용이다. 아직 확정은 아니다. "검토 의견"은 discovery 쪽 의견이다.

### 8-1. system tag 여러 개, 유저 태그는 열어 두기

- **오너 공유**
  - topic은 없앤다. 대신 topic과 같은 역할로 note에 **system tag**를 단다.
  - topic은 한 가지로만 정해야 해서 애매한 경우가 있었다. 예를 들어 마운자로 이야기는 의료로도, 다이어트로도 볼 수 있다. system tag는 **여러 개를 달 수 있게** 한다.
  - 유저가 직접 tag를 다는 것은 정해지지 않았다. 지금은 없다고 보되, 나중에 달 수 있게 열어 둔다.
  - 추천이든 shout든 **system tag로 후보를 1차 필터링**하고, 그 안에서 후보들의 note embedding으로 대상을 추린다.
- **검토 의견**
  - tag 필터는 하드 컷이라 **recall이 걱정된다.** 질문에서 tag를 잘못 뽑거나 빠뜨리면, 답할 수 있는 사람이 embedding 단계에 오기도 전에 빠진다.
    - 질문에서도 tag를 여러 개 뽑아 OR로 매칭한다.
    - 필터 결과가 너무 적으면 tag 없이 embedding만으로 검색하는 폴백을 둔다.
  - **tag의 넓이를 섞어서 달면 계층을 대신할 수 있다.** 예를 들어 `마운자로`, `비만 치료제`, `다이어트`, `의료`를 함께 단다. (→ 2026-10-29: 등록된 tag 키는 영어로 두자는 의견이다. §12-5) 구체적인 tag → 넓은 tag 순으로 범위를 넓힐 수 있다. topic 계층이 하던 일을 tag가 맡고, §8-6 shout 범위의 축이 된다.
  - 유저 태그를 나중에 열려면 저장할 때 tag의 출처를 구분해 둔다(`source: system | user`).

### 8-2. 친구 관계 대신 대화 이력 목록

- **오너 공유**
  - 첫 제품에서는 **친구 관계가 없다.** 나중에 들어갈 수 있다.
  - 대신 두 목록이 관리된다.
    - 내 portal에 와서, 공개된 note를 바탕으로 내 ami와 대화한 유저 목록
    - 내가 다른 유저의 portal에 가서 대화한 유저 목록
  - **두 목록은 양쪽 유저가 모두 볼 수 있다.**
  - **방문자가 내 ami와 나눈 대화 내용을 나도 볼 수 있다.**
- **검토 의견**
  - 두 목록은 방향이 다른 신호라 구분해서 저장한다.
    - 나에게 와서 대화한 사람: 그 사람이 나에게 관심을 보였다. 그리고 그 대화를 나도 볼 수 있으니 서로 "아는 사람"에 가깝다.
    - 내가 가서 대화한 사람: 그 사람의 note가 나에게 쓸모 있었다. 답할 능력 쪽 신호에 가깝다.
  - 지금 discovery의 `interactions`/`room_turns`가 이미 누가 누구의 agent와 대화했는지를 방향까지 담아 기록한다. 개념적으로는 기존 데이터의 연장선이다. 원본 목록은 소유 서비스가 갖고 discovery는 이벤트로 받는 지금 방식이 자연스럽다.
  - 두 목록을 양쪽 모두 볼 수 있으니, 대화 이력을 shout 대상 선정에 써도 유저에게 설명할 수 있다("전에 이야기 나눈 분이라서").

### 8-3. note 공개 범위

- **오너 공유**: 공개/비공개 두 가지만 있다. **기본은 공개**이고, 유저가 비공개로 바꿀 수 있다.
- **검토 의견**
  - 지금 discovery의 tier 구조(친구 tier 포함)를 공개/비공개로 단순화할 수 있다.
  - 비공개 전환은 §5-1의 공개 범위 변경 이벤트로 받는다. 답을 만들기 직전 원본 재조회(§5-5)도 그대로 필요하다.
  - 기본이 공개라서, publish 확인 화면(§3-2)에서 "다른 사람의 질문에 답하는 재료로도 쓰인다"는 안내가 더 중요해진다.

### 8-4. 익명성

- **오너 공유**
  - shout에 익명성은 없는 게 좋다. 받는 사람은 누가 물었는지 안다.
  - 익명 shout는 나중에 별도 기능으로 추가될 수 있게 열어 둔다.
- **검토 의견**
  - shout 문서 §6의 "요청자는 기본 익명"을 바꿔야 한다.
  - 익명 shout를 나중에 넣을 수 있게 shout 원장에 `anonymous` 같은 필드 자리만 생각해 두면 된다. 첫 제품에서는 항상 false다.

### 8-5. 이미 대화한 유저

- **오너 공유**
  - 답 생성 추천과 shout에서는 이미 대화한 유저도 당연히 다시 쓴다.
  - "대화해 보세요" 추천에서는 이미 대화한 사람을 앞에 두면 새로운 사람을 만날 기회가 줄어든다. **순위를 내린다.**
- **검토 의견**
  - 답 생성 추천: 이미 대화한 사람의 note가 답에 쓰이면 출처로 그대로 보여준다.
  - shout: 대화 이력은 같은 범위 안에서 **순위를 올리는 가산**으로 쓴다(§8-6).
  - "대화해 보세요": 제외가 아니라 감점으로 둔다. 후보가 적을 때는 이미 대화한 사람도 나올 수 있어야 한다. 화면에 "다시 이야기해 보기"처럼 표시하는 것도 고려할 만하다.

### 8-6. shout 범위(확성기) 아이디어

- **오너 공유**
  - shout는 보내는 범위를 조절할 수 있게 한다. 확성기에 비유하면 작은 소리는 좁은 후보 집단에게, 큰 소리는 더 넓은 후보에게 간다.
  - 각 단계를 유저가 받아들이기 좋게 어떻게 정의할지는 정해지지 않았다.
- **검토 의견 (아이디어, 결정 아님)**
  - **넓히는 축은 tag의 넓이로 한다.** 첫 제품에 친구 관계가 없으니 관계 거리는 축으로 쓸 수 없다. 대화 이력은 같은 단계 안에서 순위를 올리는 가산으로만 쓴다.
  - **단계 이름보다 "누구에게 들리는지"와 예상 인원을 보여준다.** 기준 tag를 문장에 넣는다. 예:

    > 🔈 작게: 마운자로에 대해 note를 남긴 사람들에게 (약 4명)
    > 🔉 보통: 비만 치료제나 다이어트 경험이 있는 사람들에게 (약 20명)
    > 🔊 크게: 건강·의료 쪽에 관심 있는 사람들에게 (약 100명)

  - **작게 시작하고, 답이 없으면 키울지 묻는다.** "6시간 동안 답이 없어요. 조금 더 크게 물어볼까요?" shout 문서의 차수를 유저에게 보이는 형태로 바꾼 것이다. 처음에 "답이 없으면 자동으로 키우기"를 고를 수도 있다.
  - **소리가 클수록 받는 쪽 알림은 약하게 한다.** 작게는 직접 알림(push), 크게는 알림 없이 "물어보는 질문들" 같은 피드에 올라가 관심 있는 사람이 가져간다. 넓게 보낼수록 스팸 부담이 커지는 문제를 구조적으로 막는다.
  - **큰 소리는 횟수를 제한한다.** 예: 크게는 하루 1번. 제한이 있어야 단계에 의미가 생긴다.
  - **시스템이 적당한 크기를 제안한다.** 구체적인 tag의 사람이 충분하면 작게를, 거의 없으면 처음부터 보통을 제안한다. 예상 인원이 0명인 단계는 보여주지 않는다.
  - **유저가 고른 크기는 받는 사람 쪽 상한을 넘지 못한다.** shout 문서 §5-4의 주간 상한, 쿨다운, mute는 큰 소리에도 그대로 적용된다. 큰 소리로 할 수 있는 것은 후보 범위를 넓히는 것까지다.
  - 이전에 냈던 "소리가 클수록 익명성을 높인다"는 아이디어는 §8-4에 따라 뺀다.

## 9. 기존 구조를 전제로 두지 않은 재설계 의견 (검토 의견)

2026-10-21에 오너가 "기존 agent-discovery에 얽매이지 말고, 이 목표를 이루기 위해 바꾸는 게 좋을 것"을 물었다. 이 절은 그에 대한 discovery 쪽 의견이고 결정이 아니다.

목표는 다음과 같다.
- 질문 → note로 답하고 출처의 사람을 추천 → 안 되면 사람만 추천 → 안 되면 shout
- 유저는 이 흐름과 별개로 **shout를 직접 던질 수도 있다**(오너 공유, 2026-10-21)

### 9-1. 추천 타입 여러 개 → 검색 파이프라인 하나, 입구 둘

지금은 타입 ①②③④가 따로 있고 API·후보 소스·랭킹이 다 다르다. 새 목표에서는 모든 흐름이 **같은 note 검색**에서 출발하고, 입구만 둘이다.

```text
[입구 1] 질문 (ami와 대화 중)
[입구 2] 명시적 shout (유저가 직접 범위를 골라 던짐)
   ↓
질문 분석: system tag 후보 여러 개 + embedding
   ↓
note 검색: tag 필터(OR) + 벡터 검색 + 키워드 검색. 결과가 적으면 tag 없이 폴백
           (2026-10-28: 키워드 검색 대신 entity 일치를 검토, §12-3)
   ↓
리랭킹
   ↓
결과 묶음
   ├ 근거 note들 (답 생성용)
   ├ owner 단위로 묶은 사람 후보 (대화해 보세요용)
   └ shout 범위별 후보와 예상 인원
```

- **질문 입구**: 결과 묶음 하나로 세 단계를 모두 판단한다. 단계마다 다시 호출하지 않으니, 같은 후보 기준으로 일관되게 판단하고 지연 시간도 한 번만 든다.
- **명시적 shout 입구**
  - 지금 shout 문서는 `nobody_covers`가 난 추천의 `recommendation_id`가 있어야 shout를 만들 수 있다. 이 조건을 **선택 사항**으로 바꾸고, 질문 자체를 받아 같은 검색으로 받는 사람을 고른다.
  - 앞 단계 없이 바로 들어오는 경로가 생기므로 요청자 쪽 상한(하루 횟수, 동시에 열려 있는 shout 수)이 더 중요해진다.
  - 선택 사항으로, 이미 답이 될 만한 note가 있으면 "이런 note도 있어요"를 함께 보여줄 수 있다. shout를 막지는 않는다.

### 9-2. "답할 수 있나" 판단은 ami에게

지금 knowledge 문서에서는 discovery가 LLM judge로 covers를 판정한다. 새 목표에서는 어차피 ami가 근거 note로 답을 쓴다. 답을 직접 써 보는 쪽이 답할 수 있는지를 가장 정확히 안다.
- discovery는 **근거와 후보를 잘 찾는 것**에 집중한다. 요청 경로에서 LLM은 질문 분석에만 쓰거나 쓰지 않는다.
- ami가 답을 시도하고, **실제로 인용한 note**를 돌려준다. 그 note의 owner가 함께 추천할 사람이다.
- 답을 못 쓰면 같은 결과 묶음의 사람 후보로 넘어가고, 그것도 없으면 shout를 제안한다.

판정 결과와 실제 답이 어긋나는 문제(covers라고 판정했는데 답은 빈약함)가 사라지고, 어떤 note가 실제로 쓰였는지가 정확히 남는다.

### 9-3. 저장소는 PostgreSQL 하나로

지금은 PostgreSQL과 DynamoDB를 함께 쓴다. 새 구조의 핵심 데이터는 다음과 같다.
- note 인덱스: embedding, tag, 공개 여부, 버전
- tag 목록
- 대화 이력 목록 사본
- 인용·전환 기록
- shout 원장

전부 관계형이고 서로 join해서 쓴다. **PostgreSQL + pgvector 하나**로 가면 공개 여부 필터, tag 필터, 벡터 검색을 한 쿼리로 할 수 있고, 첫 제품 규모에서는 운영할 것도 절반으로 줄어든다. 결정 로그처럼 양이 많은 append 데이터만 나중에 분리를 검토한다.

### 9-4. 버리는 것

| 버리는 것 | 이유 |
|---|---|
| topic 카탈로그, `visible_topic_rows`, `catalog_edges` | system tag가 대체한다 |
| topic 성숙도·점수 | note 단위 신호로 대체한다(§9-6) |
| CF 후보와 그 worker loop들 | 첫 제품에서는 "비슷한 사람"보다 "이 질문에 답할 note"가 핵심이다. 데이터가 쌓인 뒤 다시 검토한다 |
| popularity를 순위 가산으로 쓰는 것 | shout에서처럼 부하 감점으로만 남긴다 |
| friends tier와 공개 범위 tier 계산 | 공개/비공개 두 가지로 단순화한다(§8-3) |
| topic 전제의 R 결정들, 타입별 API | 파이프라인 하나로 합친다(§9-1) |

### 9-5. 그대로 가져가는 것

- 이벤트로 원본을 미러링하는 구조. 원본은 소유 서비스에 있고 discovery는 사본만 가진다(§5).
- 탈퇴 처리(`departed_users`)와 tombstone 순서 보장
- 보존 기간 sweep
- 결정 로그. 디버깅과 평가에 필요하다.
- shout 원장과 받는 사람 상한·쿨다운·mute

### 9-6. 새로 필요한 것

- **tag 목록 관리**
  - system tag는 등록된 tag에서 먼저 고르고, 없을 때만 새로 만든다(§4-2).
  - 각 tag에 넓이(구체적 ↔ 넓음)와 tag 간 관계(유사도, 동시 출현)를 둔다. shout 범위 단계가 여기서 나온다(§8-6).
  - tag를 붙이는 것은 note 생성 쪽이다. 그래서 목록 원본도 그쪽이 갖고 discovery는 미러링하는 편이 경계가 맞다. → 2026-10-28: discovery가 붙이고 목록 원본도 갖는 쪽으로 바꾸자는 의견이다(§12-4, 결정 아님).
- **note 단위 품질 신호** (성숙도 대신)
  - 답에 인용된 횟수
  - 인용 뒤 실제로 대화가 시작됐는지(전환)
  - 도움이 됐다는 피드백
  - 최근성
- **사람 단위 신호**
  - 대화 이력(방향 구분, §8-2)
  - shout 응답률
  - "대화해 보세요"에서는 이미 대화한 사람을 감점한다(§8-5).
- **답 직전 원본 재조회**: 삭제되거나 비공개로 바뀐 note가 인용되지 않게 한다(§5-5).

### 9-7. 평가 방식

지금의 10만 명 합성 모집단은 topic을 공개하는 사람들로 만들어져 있어서 새 구조를 검증할 수 없다. 대신 **합성 note + 질문 세트**를 만들어 아래를 잰다.

| 지표 | 무엇을 보나 |
|---|---|
| 검색 recall@k | 답이 있는 note가 후보에 들어오는가 |
| tag 필터 손실률 | tag 필터 때문에 빠진 정답 note가 얼마나 되는가 |
| 인용 정확도 | ami가 인용한 note가 실제로 답을 뒷받침하는가 |
| 단계 분포 | 답 생성 / 사람만 / shout 비율 |

받는 사람의 응답률처럼 실제 사람의 반응은 지금처럼 dev에서 잰다.

### 9-8. 규모

규모로 보면 기존 서비스를 고치는 것보다 새 서비스를 만드는 것에 가깝다. 이벤트 처리, 탈퇴 처리, 원장 같은 기반 코드는 상당 부분 옮겨 쓸 수 있다. 이 방향을 따른다면 knowledge 문서와 shout 문서를 고치기보다 **새 기획 문서**로 쓰고, 두 문서는 참고용으로 남기는 편이 낫다.

## 10. 2026-10-22 추가 논의: 추천 흐름과 shout 대상 선정

### 10-1. 단계와 판단 주체

- **오너 공유**

| 단계 | 판단 주체 | discovery가 할 일 |
|---|---|---|
| 1. 내 ami가 답할 수 있나 | bourbon-agent | 없음 |
| 2. 다른 ami가 **자기 note로** 답할 수 있나 | 답 생성은 bourbon-agent. 지금은 검증을 위해 discovery 실험에서 생성한다 | 답이 되는 note를 가진 ami 찾기 |
| 3. shout | discovery | 답해 줄 수 있을 것 같고 관심도 있을 것 같은 유저 찾기(§10-2) |
| 직접 shout | discovery | 3과 같다. 입력은 유저가 쓴 질문 하나다 |

- **검토 의견**
  - §9-2(답할 수 있는지는 답을 써 보는 쪽이 판단)와 맞는다. 2단계에서 discovery는 근거 note와 그 owner를 찾아 넘긴다.
  - 이전 흐름의 "답 없이 사람만 추천" 단계는 이 설명에 따로 없다. note로 답은 못 하지만 관련 있는 사람이 있는 경우는 shout 대상 찾기로 넘어간다고 본다.

### 10-2. shout 대상 선정의 기준

- **오너 공유**
  - 기준은 "이미 쓴 note로 답할 수 있나"가 아니라 **"이 사람이 답해 줄 수 있을까, 관심 있을까"**다.
  - 유저가 가진 note와 system tag 구성이 그 유저의 관심사와 지식을 대변한다. 이것을 근거로 판단한다.
  - 유저가 직접 shout를 할 때도 같다. 유저가 쓴 질문으로 같은 방식으로 대상을 찾는다.
- **검토 의견**
  - 판단 단위가 note 하나가 아니라 **유저 프로필**(note들과 tag 구성 전체)이다. 사람은 쓴 것보다 많이 알기 때문에, 질문에 맞는 note가 없어도 관심사의 모양으로 판단해야 한다.
  - 2026-10-21 실험의 범위 넓히기 결과(`ami-note-retrieval-experiment.md` §3)는 이미 쓴 note로 답할 수 있는 사람에게 닿는지를 쟀다. 이것은 2단계의 기준이지 shout의 기준이 아니다.
  - 그래서 유저마다 **note로 쓰지 않은 경험**을 따로 두고 추가 실험한다. 선정 방법은 공개된 note와 tag만 보고, 판정 모델은 쓰지 않은 경험까지 보고 "답할 수 있음"과 "관심 있음"을 정한다. 비교하는 선정 방법은 아래와 같다.
    - tag 프로필 매칭
    - note embedding(유저별 최대, 상위 3개 평균, 중심)
    - 위 두 가지의 결합
    - 결합 상위 후보를 LLM이 유저 프로필(tag 구성과 note 제목)을 읽고 재순위
    - tag 넓이 단계별 후보 집합
  - 답할 **의향**(최근 활동, 응답 이력)은 합성 데이터로 잴 수 없어서 이 실험의 범위 밖이다.

## 11. 2026-10-27 추가 논의: tag 두 층, 사람 신호, 재순위

`new-type/ami-note-retrieval-experiment.md`(이하 실험 문서)의 결과를 보고 나눈 이야기다. 다음 실험 계획은 `new-type/ami-note-next-experiments-plan.md`(이하 실험 계획)에 있다.

### 11-1. system tag를 topic tag와 registry tag 두 층으로

- **오너 의견**
  - system tag는 기존 topic 체계처럼 **topic 목록에서 골라** 붙인다. 다만 한 개가 아니라 **여러 개**를 붙일 수 있다.
  - 실험에서 쓴 "등록된 tag에서 고르기" 방식은 **추가 tag**로 둔다. 한 note에 두 종류가 함께 붙는다.
  - 이득이 있다면 topic 목록에서 붙인 것은 **topic tag**로 구분한다.
  - topic 목록이 담지 못하는 것은 목록에 없는 tag를 새로 만들어 붙이고, 그런 tag는 **registry로 관리**한다.
- **검토 의견**
  - **앞 절의 판단을 뒤집는다.** §2-3은 카탈로그 계층을 tag 간 유사도로 대체한다고 했고, §2-4와 §9-4는 topic 카탈로그와 `catalog_edges`를 버린다고 했다. 이 구조를 따르면 카탈로그와 계층은 topic tag로 다시 쓴다. 버리는 것은 topic 단위 검색(`visible_topic_rows`)과 topic 점수·성숙도다.
  - 실험에서 남은 문제를 이 구조가 직접 줄인다.
    - **동의어:** tag 필터가 놓친 정답은 대부분 동의어(`child care` / `childcare`, `bouldering` / `climbing`) 때문이었다. 카탈로그는 별칭(aliases)이 있어서 `childcare`가 이미 `child care`의 별칭이고, `bouldering`은 `rock climbing > climbing` 아래에 있다.
    - **넓히기:** LLM이 매번 정하는 넓이(specific/mid/broad) 대신 카탈로그 계층을 따라 넓힌다. "보통"과 "크게"가 일관되게 정해진다. 다만 "작게"를 registry tag로 정하면 여전히 자주 비어 있을 수 있어서, 비어 있으면 다음 단계부터 보여준다(§8-6). 최상위 topic에서는 더 올라갈 곳이 없고, 한 단계 올라갈 때 인원이 크게 뛰는 곳도 있다(예: `health` 아래는 카탈로그의 17%). 실험 계획 A에서 잰다. → 2026-10-28: 실험 뒤 검토 의견은 등록된 tag의 넓이로 넓히는 쪽이다(§12-1).
    - **지역 노이즈:** 카탈로그에 한국 도시는 없다. 다만 국가는 system topic으로 들어 있어서 장소 규칙은 따로 정해야 한다(아래).
  - **역할 분담**

    | 종류 | 맡는 것 | 쓰는 곳 |
    |---|---|---|
    | topic tag | 넓은 분야, 중간 분류 | tag 필터, shout 범위 넓히기, 유저 관심사 프로필 |
    | registry tag | 제품·브랜드·약 이름, 세부 주제 | 정확히 일치할 때 가산, portal 표시, shout "작게" 단계 |

  - **기존 topic 카탈로그를 그대로 쓸 수 있다.** agent-discovery-api의 `data/catalog_dist/catalog.json`이다.
    - bourbon-topic-api가 2026-09-22에 만든 것을 복사해 둔 것이다. Wikidata 덤프 `20260802` 기반이다.
    - active topic 3,161개, active topic 사이의 부모-자식 edge 3,107개, 최상위 topic 63개다. 대부분 깊이 1~3이고, 부모가 둘 이상인 topic은 9개뿐이다.
    - 한국어·영어·일본어 이름과 별칭이 있다.
  - **실험 tag와 맞춰 보면** registry tag 415종 중 56종이 카탈로그 이름·별칭과 문자열로 정확히 같다. 사용 횟수로는 43%다. 문자열 일치만 센 것이라 LLM이 고르면 더 높아질 것이다.
    - 잘 맞는 것: `health`, `travel`, `wine`, `whisky`, `camping`, `parenting`, `dog training`, `espresso` 같은 분야와 중간 분류
    - 없는 것: 약 이름(`mounjaro`, `semaglutide`. "약" topic 자체가 없다), 브랜드·제품(`glendronach`, `hario v60`, `schd`), 세부 주제(`home baking`, `peaty whisky`, `sleep training`, `etf`), 한국 지명
  - **새 registry tag는 두 경우로 나눈다.**
    - topic 아래의 구체적인 이름: `peaty whisky`는 `whisky` 아래에 들어간다. topic tag와 registry tag를 함께 붙인다.
    - 어느 topic에도 맞지 않는 새 주제: registry tag만 붙는다. topic 목록에 빈 곳이 있다는 신호다.
  - **registry tag는 만들 때 부모 topic을 하나 지정한다.** 정말 없을 때만 비운다. 부모가 없으면 범위를 넓힐 때 올라갈 곳이 없다.
  - **topic으로 올리는 경로를 둔다.** 부모 없는 registry tag가 일정 수 이상의 note나 유저에게 쓰이면 topic 후보로 올리고, 검토해서 계층에 넣는다. topic 목록이 실제 사용을 따라 자란다. 원본 카탈로그는 bourbon-topic-api가 갖고 있으니, 올리는 절차는 그쪽과 맞춰야 한다.
  - **registry 안의 동의어는 여전히 관리해야 한다.** 범위는 topic이 빠진 만큼 작아진다. 새 registry tag가 생길 때 embedding 유사도로 가까운 tag를 찾고 LLM이 같은지 확인해 병합한다. → 2026-10-28: tag 이름만 embedding하지 않고 정의문과 note centroid로 표현하자는 의견이다(§12-2).
  - **"topic 먼저" 규칙이 지켜지는지 잰다.** LLM은 맞는 topic이 있어도 새 tag를 만드는 쪽으로 기울 수 있고, 그러면 자유 생성과 비슷해진다. 실험 계획 A에서 잰다.
  - **장소 규칙:** note의 주제가 장소일 때(여행지, 지역 정보)만 장소를 tag로 붙인다. 글쓴이가 사는 곳은 붙이지 않는다. → 2026-10-28: 장소는 system tag 대신 entity로 뽑자는 의견이다(§12-3).
  - **넓이 표시는 거의 필요 없어진다.** 넓은 쪽은 topic 계층이, 구체적인 쪽은 registry tag가 맡는다. §8-1의 "넓이를 섞어 달기"와 §9-6의 "각 tag에 넓이"를 이 구조가 대신한다. → 2026-10-28: 등록된 tag 주축이면 넓이를 그대로 쓰고 넓히기도 넓이로 하자는 의견이다(§12-1, 결정 아님).
  - **tag를 붙이는 쪽은 note 생성 쪽이라는 §9-6의 경계는 그대로다.** 카탈로그는 topic-api가, registry는 tag를 붙이는 쪽이 원본을 갖고 discovery는 미러링한다. → 2026-10-28: tag를 붙이는 쪽을 discovery로 바꾸고 registry 원본도 discovery가 갖자는 의견이다(§12-4, 결정 아님).

- **실험 결과 (2026-10-27, 실험 문서 §8·§9)**
  - 카탈로그 topic을 system tag의 주축으로 쓰면(T, TR) 검색은 등록된 tag(R)와 비슷하다. 하지만 shout 단계가 거칠어진다. 처음으로 사람이 있는 단계가 8명 / 0.78에서 20명 / 0.67이 된다.
    - 원인은 카탈로그 topic의 세밀함이 분야마다 다르다는 점이다. `gear and collecting` 같은 통 topic이 있고, R의 중간 tag(weight loss, auto camping 등)에 해당하는 층이 없다.
  - 재순위 전의 직접 경험자 hit@5도 0.537 → 0.432로 떨어진다(신뢰구간 [−0.179, −0.032], 계획에서 기준을 정한 지표는 아님). 채택한 흐름인 B1 재순위 뒤에는 점 추정 −0.063(신뢰구간 [−0.126, 0.000])으로, 실행 전에 정한 "나쁘지 않다" 기준(하한 −0.05 이상)을 통과하지 못했다(실험 문서 §10). R이 낫다고 보인 것은 아니고, TR을 택할 근거가 없다는 뜻이다.
  - 계획의 기준으로는 TR이 기본안이 되지 못한다. 놓친 정답이 R보다 많고(1.8% 대 1.6%), 처음으로 사람이 있는 단계의 관련 경험자 비율이 낮다(0.67 대 0.78).
  - TR의 registry tag는 검색에서는 정답을 조금 더 잡았지만, 선정에서는 보태는 것이 없었다. 부모 topic 연결은 첫 note 기준으로 고정돼 15%가 어긋났다. 장소 tag가 다른 주제에 다시 쓰인 경우가 많다.
  - R을 주축으로 두고 topic은 보완만 하는 조합(§9)에서는:
    - 검색 필터를 "R tag 일치 또는 질문 topic 주변"으로 넓히면 R이 놓치던 정답(32 / 2,014)을 거의 다 받는다(1 / 2,014). 다만 이것은 범위가 R을 포함해서 구조상 정해진 결과다. 실제 이득은 hit@5 +0.009(3문항), recall@10 +0.008로 근소하고, 후보는 약 40% 늘어난다. R이 놓친 정답은 동의어·표기 차이와 다른 분야 tag 때문이다.
    - 선정 점수에 topic을 더하면 재순위 전에는 직접 경험자 hit@5가 떨어진다(−0.053). B1 재순위 뒤에는 R과 구분되지 않는다(−0.006, −0.011, 신뢰구간이 0을 포함). 이득이 보이지 않아서 채택되지 않는다.
- **검토 의견 (실험 후, 결정 아님)**
  - 지금 근거로는 system tag를 **등록된 tag(넓이 포함)를 주축**으로 두는 편이 낫다. shout 단계의 세밀함(R이 더 세밀하고, 처음으로 사람이 있는 단계의 관련 경험자 비율이 높다. A-7 기준)과, topic 주축이 B1 재순위 뒤에도 직접 경험자 찾기에서 R보다 나쁘지 않다고 보이지 못한 점이 근거다.
  - 카탈로그 topic은 note에 함께 붙이고 **검색 필터를 보완하는 그물**로 쓸 수 있다. 이득은 근소하다.
  - "크게" 다음의 더 넓은 단계에 topic을 쓰는 것은 참고값만 있다. 관심 분야 밖 직접 경험자에게 19문항 중 3문항 더 닿았지만, 유저 절반 이상에게 보낸다.
  - 선정 점수에는 topic을 넣지 않는다. B1 재순위 뒤에 이득이 보이지 않았다.
  - portal 분류, 통계, 등록된 tag의 동의어 정리(카탈로그 별칭)에도 topic id를 쓸 수 있다. 매칭과는 별개다.
  - 모두 질문 95개와 카탈로그 빌드 하나의 결과다. 카탈로그를 다듬거나 통 topic을 빼면 오너가 낸 "topic tag 주축" 방향의 결과가 달라질 수 있다.
  - 장소 tag는 프롬프트 규칙으로 일부만 줄었다. 사후 검사가 필요하다. → 2026-10-28: 장소를 entity로 따로 뽑자는 의견이다(§12-3).

### 11-2. shout 응답 이력을 사람 신호로

- **오너 의견:** 좋은 방향이다.
- **검토 의견**
  - 실험에서 관심 분야 밖의 경험을 묻는 질문은 58%만 상위 10명 안에 직접 경험자가 있었다(실험 문서 §6). note에 드러나지 않는 경험이라 공개 정보만으로는 한계가 있다. 누가 어떤 질문에 답했는지는 note보다 직접적인 신호다.
  - **받은 것도 기록한다.** 누구에게 보냈는지, 답했는지, 무시했는지, 거절했는지를 다 남긴다. "이 분야는 보내도 답하지 않는다"도 신호다.
  - **추천이 추천을 굳히지 않게 한다.** 보낸 사람만 답할 수 있으니, 이력만 따르면 처음에 뽑힌 사람만 계속 뽑힌다. 받는 사람 중 일부는 이력이 없는 사람으로 채운다. shout 문서 §5-6의 탐색 자리가 이 역할이다.
  - **같은 사람에게 몰리지 않게 한다.** 잘 답하는 사람일수록 많이 받게 된다. shout 문서 §5-4의 받는 사람 상한·쿨다운이 이 역할도 한다.
  - 원본은 shout를 가진 서비스가 갖고, discovery는 이벤트로 받는다. §9-6의 "shout 응답률"을 구체화한 것이다.

### 11-3. LLM 재순위는 다시 확인하고, "왜 이 사람인지" 설명은 따로

- **오너 의견**
  - 재순위 대신 "왜 이 사람인지" 설명을 만드는 방향은 좋다.
  - 다만 LLM 재순위가 정말 효과가 없는지는 **확실히 해야 한다.**
- **검토 의견**
  - 실험 문서 §6의 "효과가 거의 없다"는 **그 설정 하나의 결과**다. 판정 라벨로 상위 20명을 다시 줄 세웠을 때의 상한을 계산해 보면 여지가 있다. 다만 이 상한은 **판정 라벨을 아는 경우의 이론상 최대치**다. 판정 모델은 note로 쓰지 않은 경험까지 보고 라벨을 정했고, 재순위는 공개된 note만 볼 수 있다. 특히 관심 분야 밖의 경험은 note에 드러나지 않으니 그 상한까지 가기는 어렵다.

    | 질문 | 지표 | tag + embedding 결합 | 이번 LLM 재순위 | 판정 라벨 기준 상한 |
    |---|---|---|---|---|
    | 전체 95개 | 관련 경험 + 관심 p@5 | 0.84 | 0.87 | 0.98 |
    | 전체 95개 | 직접 경험자 hit@5 | 0.54 | 0.51 | 0.71 |
    | 관심 분야 밖 19개 | 직접 경험자 hit@5 | 0.32 | 0.37 | 0.74 |

  - 관련 경험 + 관심인 사람은 상위 20명 안에 충분히 있다. 직접 경험자는 질문의 71%에서만 상위 20명 안에 있고(near는 18%), 그래서 hit@5 상한이 0.71이다. 이번 재순위가 얻은 것은 관련 경험 + 관심 p@5에서 여지의 약 17%이고, 신뢰구간상 0과 구분되지 않는다. 이번 설정이 약했던 이유로 보이는 것은 다음과 같다.
    - 재순위 모델은 tag와 note **제목만** 봤다. 본문을 넣으면 공개된 정보 안에서는 판정 모델에 더 가까워진다.
    - `gemini-3.5-flash`를 low effort로 썼다.
    - 점수가 0~3 네 단계라 동점이 많았고, 동점은 원래 순서를 따랐다.
    - 질문이 95개라 ±0.03 정도의 차이는 잡음 범위다.
  - 입력, 모델, 점수 방식을 바꿔 다시 잰다(실험 계획 B). 판정 라벨을 그대로 쓰므로 재순위 호출 비용만 든다. 그래도 여지를 못 잡으면 뺀다.
- **결과와 결정 (2026-10-27)**
  - 실험 계획 B로 다시 잰 결과는 실험 문서 §7에 있다. 후보마다 질문과 가까운 note 3개의 본문을 더 읽히자(B1) 관련 경험 + 관심 p@5가 0.842 → 0.895가 됐다. 신뢰구간 [+0.027, +0.080]이고, 전체 직접 경험자 hit@5도 나빠지지 않았다. 다만 직접 경험자 hit@10은 조금 낮아졌다(0.632 → 0.600). 점 추정으로는 관심 분야 밖 질문에서 가장 크게 올랐다(19문항, 참고값).
  - effort를 올리거나 더 큰 모델을 쓰거나 점수를 둘로 나눠도 주 지표는 B1보다 낫지 않았다(점 추정).
  - **오너 결정 (이 메모에서 결정으로 기록하는 첫 항목): shout 대상 선정에 B1을 쓴다.** tag + embedding 결합으로 상위 20명을 뽑고, `gemini-3.5-flash` low effort가 tag 구성, note 제목, 질문과 가까운 note 본문 3개를 읽고 다시 줄 세운다. 한 건당 입력 약 1만 5천 토큰, 지연 약 8초다. shout는 비동기라 받아들일 만하다고 봤다.
  - **"왜 이 사람인지" 설명은 재순위와 별개다.** 질문과 겹치는 tag, 질문에 가장 가까운 note 제목으로 LLM 호출 없이 만들 수 있다. 예: "위스키·셰리 캐스크 note를 쓰셔서". 재순위를 쓰게 되면 그 출력에 이유를 함께 받을 수도 있다.

### 11-4. 제안했지만 아직 논의하지 않은 것

- **유저가 직접 표시하는 "물어봐도 되는 분야":** 관심 분야 밖의 경험을 찾는 다른 방법이다. 본인이 공개한 것이라 공개 원칙에 맞고, §8-1에서 열어 둔 유저 태그의 용도로도 좋다.
- **질문이 누구와도 잘 맞지 않으면 처음부터 넓게 제안:** "작게"가 0명이거나 가장 가까운 사람과의 유사도가 낮으면 "보통" 이상을 기본으로 제안한다(§8-6의 크기 제안을 구체화).
- **답에 섞이는 근거 밖 내용:** 모호한 질문과 두 note를 합치는 질문에서 13~19%의 답에 일반론이 섞였다(실험 문서 §4). 문장마다 인용을 달고 인용 없는 문장을 빼는 사후 검증, 또는 "다른 분들의 경험"과 "ami의 의견"을 나눠 보여주는 방식이 있다. 답은 bourbon-agent가 만들 것이니 그쪽에 전달할 요구사항이다.

## 12. 2026-10-28~29 추가 논의: 실험 뒤의 설계 방향, 짧은 텍스트 embedding, 고유명사, tag 담당, tag·entity 언어

실험 A~D(실험 문서 §7~§10)를 마치고 정리한 설계 방향과, 그에 대해 나눈 이야기다. 결정은 아니다. 확정된 것은 여전히 §11-3의 B1 채택뿐이다.

### 12-1. 실험 결과를 바탕으로 한 설계 방향 (검토 의견)

- **흐름**
  - §10의 세 단계를 그대로 따른다. 내 ami가 답할지는 bourbon-agent가 판단한다. 다른 사람의 note로 답하기와 shout는 discovery의 같은 note 검색 파이프라인을 쓴다(§9-1). 입구만 둘이다.
- **system tag**
  - 주축은 **등록된 tag**다. 넓이(specific/mid/broad)를 포함하고, note당 3~6개를 붙인다. 검색 필터, shout 범위 단계, 선정 점수에 쓴다.
  - **카탈로그 topic**은 note당 1~3개를 함께 붙인다. 검색 필터를 보완하는 그물, portal 분류와 통계, 등록된 tag의 동의어 정리에 쓴다. 선정 점수에는 넣지 않는다(§11-1, 실험 문서 §10).
  - 넓이는 tag가 처음 등록될 때 정하고 목록에 고정한다. 같은 tag가 note마다 다른 넓이를 받지 않게 하기 위해서다.
  - 등록된 tag의 키는 영어이고, 처음 등록될 때 한국어 표시 이름을 함께 만들어 고정한다(§12-5).
  - 장소는 system tag로 붙이지 않고 entity로 따로 뽑는다(§12-3). §11-1의 장소 규칙을 대신한다.
- **검색 (다른 사람의 note로 답하기)**
  - 질문에도 등록된 tag와 topic을 붙인다. 등록된 tag는 목록 안에서만 고른다.
  - 후보는 "등록된 tag 일치 **또는** 질문 topic 주변"이다. 순위는 note 본문 embedding으로 매긴다. 필터 결과가 20개보다 적으면 embedding만으로 검색한다.
  - 질문에 고유명사가 있으면 entity 일치를 더한다(§12-3).
  - tag가 아직 붙지 않은 note는 필터와 상관없이 후보에 넣는다(§12-4).
  - 상위 8개를 bourbon-agent에 넘긴다. 답에 일반론이 섞이는 문제는 §11-4에 적은 요구사항으로 전달한다.
- **shout 대상 선정**
  - 등록된 tag 프로필 점수와, 질문과 가장 가까운 그 사람의 note 3개의 유사도 평균을 각각 표준화(z-score)해 더한다. 그 순서로 상위 20명을 뽑고 B1으로 다시 줄 세운다(§11-3).
  - shout 범위는 등록된 tag의 넓이로 나눈다. 실험 값은 작게 2명 / 0.83, 보통 11명 / 0.77, 크게 24명 / 0.67이다(실험 문서 §8). 0명인 단계는 보여주지 않는다(§8-6).
  - topic 계층으로 넓히는 "더 크게" 단계는 참고값만 있다(52명 / 0.51, 실험 문서 §9). 유저 절반 이상에게 보내므로 첫 제품에서는 빼거나 알림 없는 피드 단계로 둔다.
  - 사람 신호(§11-2): shout 응답 이력, 탐색 자리, 받는 쪽 상한을 둔다. 대화 이력 목록(§8-2)은 같은 단계 안의 가산으로만 쓴다.
  - "왜 이 사람인지" 설명은 겹치는 tag와 가장 가까운 note 제목으로 LLM 없이 만든다. 상호명·지명 entity는 드러내지 않는다(§12-3).
- **운영 비용 (실험 기준, 입력 토큰)**

  | 작업 | 모델 | 단위당 대략 |
  |---|---|---|
  | note tag 붙이기 (등록된 tag + topic) | `gemini-3.5-flash` low | note 1개당 약 2~5천(중간값 4.4천) |
  | 질문 tag 붙이기 | `gemini-3.5-flash-lite` low | 질문 1개당 약 4~5천(topic + registry 호출 기준). R tag만 고르는 호출은 약 2.9천 |
  | shout 재순위 (B1) | `gemini-3.5-flash` low | shout 1건당 약 1만 5천, 지연 약 8초 |

  tag 붙이기 프롬프트에는 등록된 tag 목록 전체가 들어간다(실험에서 약 400개). 목록이 커지면 비용도 함께 커진다.

- **2026-10-29에 잰 것 (실험 문서 §11~§14)**
  - **목록이 커질 때 (§11):** 가까운 tag 50개만 보여주면 검색과 선정에는 아직 큰 해가 없다. 하지만 새 tag가 두 배로 는다(목록 860 대 444). gshort에만 있는 tag의 절반 남짓(547개 중 285개)이 한 번만 쓰인, 잘게 쪼갠 이름이다. 미리 정한 판단은 판단 불가였다. 기준 밖으로 보면 "가까운 tag만 보여주기"를 그대로 쓰기는 어려워 보인다. 다음 후보는 다음 둘이다.
    - LLM이 자유롭게 제안하고, 등록된 tag에 맞춰 LLM이 확인한다(§12-2와 같은 구조).
    - 넓은 tag와 중간 tag는 늘 함께 보여준다.
  - **note가 적은 유저 (§12):** 유저의 40%가 note 1개인 구성에서도 하락은 미리 정한 경고선(0.10) 아래였다. 다만 상위 5명에는 note 1개인 직접 경험자가 13%만 든다(note 10개는 20 seed로 74%). B1 탓이 아니라 재순위 전 선정 점수부터 그렇다. 선정 점수에서 note 수의 차이를 보정하거나, shout 문서 §5-6의 탐색 자리를 두는 것이 필요할 수 있다.
  - **판정 모델 편향 (§13):** 다른 계열 판정 모델로도 B1 효과는 유지됐다. 직접 경험 라벨은 두 판정이 잘 맞는다. 하지만 "관련 경험" 라벨은 크게 갈렸다(kappa 0.21). 그래서 shout 범위 단계의 관련 경험자 비율처럼 그 라벨에 기댄 절대값은 믿기 어렵고, 같은 판정 안의 비교도 B1 효과 말고는 다시 재지 않았다. §11-1에서 TR을 택하지 않은 근거 중 "0.78 대 0.67"도 이 라벨에 기댄다. 다른 근거(놓친 정답, 직접 경험자 hit@5)는 영향이 작다.
- **아직 재지 않은 것**
  - note 1만 개 이상의 규모
  - note가 1~3개뿐인 유저(cold start, §3-6)
  - 옛 note와 새 note의 의견이 다를 때
  - 표시용 요약 레이어만 있을 때(결정 항목 3)
  - 실제 사람의 응답률과 피로도(dev에서만 잴 수 있다)
  - 판정 모델과 데이터 생성 모델이 같은 데서 오는 편향 → 2026-10-29에 일부 쟀다(위, 실험 문서 §13)

### 12-2. 짧은 tag·topic의 embedding 유사도

- **오너 의견:** topic과 tag는 한두 단어인 경우가 많은데, embedding 유사도로 찾고 붙이면 품질이 나쁘지 않을까.
- **검토 의견**
  - **짧은 텍스트끼리 비교하면 나쁜 게 맞다.** §4-1과 같은 이유다. 중의어(`java`, `football`)를 가르지 못하고, 철자가 비슷한 tag끼리는 의미가 달라도 가깝게 나온다.
  - **실험에서는 짧은 텍스트끼리의 비교를 대부분 피했다.**
    - topic은 이름만 넣지 않았다. 영어·한국어 이름, Wikidata 영어 설명, 별칭 최대 8개를 합친 문장으로 embedding했다.
    - note 쪽은 한국어 문단 하나다. 결국 문단과 짧은 설명문을 비교한 셈이다.
    - embedding은 후보 topic 50개를 뽑는 데까지만 썼다. 고르는 것은 LLM이 설명을 읽고 했다.
    - registry tag의 부모 topic도 그 note의 후보 50개에서 LLM이 골랐다.
    - tag 이름을 그대로 embedding한 곳은 "topic 먼저" 검사기 하나다. 그래서 검사기는 note의 후보와 tag 자신의 가까운 topic을 합쳐서 봤다.
  - **재지 않은 것이 있다.** 맞는 topic이 후보 50개 안에 들어오는지(후보 recall)는 따로 재지 않았다. RT-필터가 질문 topic에 기대고 있어서 질문 쪽 후보 recall도 함께 잰다. 실험 계획 F에서 잰다.
  - 부모 연결이 15% 어긋난 것(§11-1)은 대부분(175회 중 164회) 부모를 첫 note 기준으로 고정한 채 다른 note에 다시 쓴 데서 왔다(실험 문서 §8). 후보 recall로 설명될 수 있는 것은 처음 만든 note의 11회뿐이다.
  - **짧은 tag끼리 비교해야 하는 곳은 운영에서 생긴다.** 동의어 병합, 그리고 질문 tag를 등록된 tag에 맞추는 일이다. §11-1의 "embedding 유사도로 가까운 tag를 찾고 병합한다"를 아래처럼 바꾸자는 의견이다.
    - **tag는 이름이 아니라 쓰임으로 표현한다.** 처음 등록될 때는 tag 이름, LLM이 쓴 한 줄 정의, 첫 note를 합친 문장으로 embedding한다. note가 쌓이면 그 tag가 붙은 note embedding의 평균(centroid)으로 바꾼다.
    - **동의어는 세 단계로 판정한다.**
      1. 표기를 정규화한다(`child care` / `childcare`, 대소문자, 악센트, 문장부호).
      2. 카탈로그 별칭과 centroid 유사도로 후보를 뽑는다.
      3. 같은 것인지는 LLM이 정의와 예시 note를 읽고 판정한다.
    - **embedding은 후보를 뽑는 데까지만 쓰고,** 판정을 맡기지 않는다.

### 12-3. 고유명사(지명, 상품명, 상호명)는 entity로 따로

- **오너 의견:** 질문이 특정 이름에 관한 것이면 그 이름이 note에 남아 있는 게 좋지 않을까. 나중에 원문 BM25 검색을 보완하는 데 좋을 것 같다.
- **검토 의견**
  - **질문이 그 대상에 관한 것이라면 가장 강한 신호다.** "성수동 ○○ 카페 가 본 사람", "갤럭시 Z 폴드 써 본 사람" 같은 질문이 그렇다. 직접 경험자 찾기에 특히 좋다.
  - **system tag에는 섞지 않는다.** 실험에서 `jeju`는 R에서 note 60개, 장소 규칙을 넣은 TR에서도 31개에 붙었다. 대부분(57/60, 28/31)이 제주에 사는 글쓴이의 다른 주제 note였다. R에서는 specific으로 등록됐지만 유저 21명의 note에 걸쳐 있어서 "작게" 단계와 선정 점수를 흐린다. 프롬프트 규칙으로는 거주지를 막지 못했다.
  - **note마다 entity를 따로 뽑는다.**

    | 항목 | 예 |
    |---|---|
    | 정규형 | `제주`, `이마트`, `GlenDronach`. 원래 언어 표기다(§12-5) |
    | 종류 | place / product / org(가게·회사·브랜드) / work(책·영화 등) |
    | 별칭 | `제주`라면 `제주도`, `Jeju`, `Jeju Island` |
    | 역할 | 주제(그 대상이 note의 주제) / 언급(지나가듯 나옴) |

  - **정규화가 핵심이다.** BM25가 약한 곳이 바로 여기다. 한영 표기(제주/Jeju), 줄임말(스타벅스/스벅), 음역(글렌드로낙/GlenDronach), 한국어 조사("제주에서", "제주도의")가 그렇다. entity를 정규형과 별칭으로 묶어 두면 원문 BM25가 놓치는 것을 받는다. 등록된 tag처럼 이미 등록된 entity와 같은 것인지 먼저 확인하고, 없을 때만 새로 만든다. 후보 찾기와 언어, 매칭 규칙은 §12-5에 있다.
  - **질문에 entity가 있을 때만 쓴다.** 그 entity가 붙은 note를 후보에 넣고 순위에 가산한다. 역할이 "주제"인 note는 크게, "언급"인 note는 작게 더한다. 실험에서 BM25를 늘 섞었을 때는 모호한 질문의 recall@10이 0.81에서 0.64로 떨어졌다(실험 문서 §2). entity가 있을 때만 켜면 그 손해를 피할 수 있을 것으로 본다. entity가 잘못 뽑히는 비율은 E에서 센다.
  - **원문 BM25는 entity와 함께 쓸지 따로 잰다.** §4-3의 "고유명사는 BM25 하이브리드"를 entity 일치로 바꾸고, BM25는 entity가 있는 질문에서만 보조로 둘지 실험 계획 E에서 정한다.
  - **지명은 카탈로그와 연결할 수 있다.** 카탈로그에 장소 topic이 218개 있다("regions of the world" 아래). 제주를 `South Korea` topic에 연결하면 "대한민국 여행 경험자"로 넓힐 수 있다. 카탈로그에는 한국 도시·섬이 없어서 그보다 세밀한 단계는 없다. 상품명과 상호명은 카탈로그에 거의 없으니 등록된 entity 목록으로 관리한다.
  - **식별 정보에 주의한다.** 상호명과 지명은 직장, 거주지, 단골집 같은 식별 정보가 되기 쉽다.
    - 비공개로 바뀐 note의 entity는 그 note와 함께 검색에서 빠진다(§3-7, §5-1).
    - 공개 note의 entity라도 상호명·지명은 portal이나 "왜 이 사람인지" 설명에 드러내지 않는다.
    - 글쓴이가 사는 곳은 프롬프트 규칙만으로 막지 못했다(위). 뽑을 때 "언급"으로 두게 하고, 사람 단위 점수에서는 "언급" place entity의 가산을 작게 둔다. 실제 서비스에서 discovery가 유저의 거주지를 알 수 있을지는 정해지지 않았다. 그래서 거주지 정보 없이도 동작하는 규칙으로 둔다. 누출 비율은 E에서 합성 유저의 거주지로 직접 센다.
  - **지금 질문 세트로는 효과를 잴 수 없다.** 고유명사 질문(single)은 note의 고유명사가 그대로 들어가 embedding이 이미 1.0이었다(실험 문서 §2, 한계). 표기를 바꾸고 entity를 짚는 질문을 따로 만들어 잰다(실험 계획 E).

### 12-4. system tag는 discovery가 붙이고 관리

- **오너 의견:** tag는 discovery를 위한 데이터다. note 생성 쪽은 note 생성만 맡고, tag는 discovery가 붙이고 관리하는 게 좋겠다.
- **검토 의견: 동의한다. §9-6과 §11-1의 "tag는 note 생성 쪽이 붙인다"를 바꾸자는 의견이다.**
  - 앞의 판단은 "의미 데이터는 원본 옆에 둔다"는 원칙에서 나왔다. 실험을 해 보니 system tag는 note의 의미라기보다 **검색 인덱스**에 가깝다.
  - **검색 품질과 함께 바뀐다.** tag 체계, 프롬프트, 모델, 병합 규칙은 검색 결과를 보며 계속 고칠 대상이다. 실험 A~D만으로도 여러 번 바뀌었다.
  - **다시 붙이는 일이 잦다.** 체계를 바꿀 때마다 전체 note를 다시 tag해야 한다. discovery는 note 사본을 갖고 있으니(§5) 자기 일정대로 배치를 돌릴 수 있다.
  - **관리할 것이 한 곳에 모인다.** 등록된 tag 목록, 동의어 병합, entity와 그 정규화, 카탈로그 미러, 질문 tag가 모두 discovery에 있다. 이벤트 worker를 소비하는 쪽 repo에 두는 기존 원칙과도 맞다.
  - **note 생성 쪽은 note 생성에만 집중한다.** discovery 사정으로 그쪽을 배포할 일이 없어진다.
  - 카탈로그 원본은 그대로 bourbon-topic-api가 갖고 discovery가 미러링한다. registry tag를 topic으로 올리는 절차(§11-1)는 discovery와 topic-api 사이의 일이 된다.
- **함께 챙길 것**
  - **portal 표시:** portal이 tag로 분류하거나 보여준다면 discovery가 tag를 읽기 API로 주거나 `tags-updated` 같은 이벤트를 낸다. portal이 discovery에 의존하게 되므로, 표시용 분류가 꼭 필요한지 함께 정한다.
  - **유저 tag:** 도입한다면 유저가 쓴 note의 일부이니 note 쪽 원본에 두고, discovery는 다른 필드처럼 사본으로 받는다(`source: user`, §8-1).
  - **수정과 순서:** tag 결과에 note 버전을 함께 저장한다. 수정 이벤트가 오면 다시 tag하되, 늦게 끝난 옛 버전의 결과가 새 버전을 덮지 않게 한다.
  - **실패 재시도:** deferq에는 재시도와 DLQ가 없다. LLM 호출이 실패하면 handler가 직접 재시도하거나, note를 "tag 안 됨" 상태로 남기고 주기 작업이 다시 집어 가게 한다.
  - **tag가 붙기 전의 공백:** publish 직후 tag가 붙기 전의 note는 필터와 상관없이 후보에 넣고 embedding 순위로만 줄 세운다. 필터 결과가 20개 이상이면 폴백이 켜지지 않으니 따로 넣어야 한다.
  - **비용:** tag 붙이기와 다시 붙이기의 LLM 비용은 discovery 쪽 비용이 된다(§12-1 표).

### 12-5. tag와 entity의 언어 (2026-10-29)

- **오너 질문:** 각 tag의 언어는 어떻게 되나. entity 때문에 물어본 것이다.
- **검토 의견 (오너 동의, 결정 아님)**

  | 종류 | 언어 |
  |---|---|
  | 등록된 tag | 키는 영어 소문자(`weight loss`). 처음 등록될 때 한국어 표시 이름을 함께 만들어 고정한다(`체중 감량`). 한국 고유 개념은 키를 로마자로 둔다(`jeonse` → `전세`) |
  | 카탈로그 topic | 키는 topic id다. 표시는 카탈로그의 한국어 이름을 쓴다 |
  | entity | 정규형은 그 대상의 **원래 언어 표기**다. 국내 대상은 한국어, 해외 대상은 원어다. 다른 언어 표기는 별칭에 둔다 |
  | 질문 tag | 질문이 한국어여도 등록된 tag는 영어 목록에서 고른다. 실험에서 한국어 질문의 tag 400개 중 399개가 등록된 tag로 매핑됐다(실험 문서 §1). 언어 때문에 놓친 사례는 따로 세지 않았다 |
  | 유저 태그 | 유저가 입력한 그대로 둔다 |

- **등록된 tag를 영어로 두는 이유**
  - 한국어는 띄어쓰기, 외래어 표기, 조사 때문에 같은 tag가 여러 개로 갈라지기 쉽다.
  - 카탈로그의 주 이름과 별칭이 영어 중심이라 맞추기 쉽다(별칭의 약 76%가 라틴 문자). 한국어 이름은 active topic 전부에 있다.
  - 실험에서 이미 영어로 붙였다(2026-10-21).
  - 한국어 표시 이름은 portal 분류와 "왜 이 사람인지" 설명에 쓴다. 실험에는 없던 부분이다.
  - 한국 고유 개념의 로마자 키는 흔들릴 수 있다(`jeonse`/`chonsei`). 한국어 표시 이름은 고정되어 있으니 동의어 병합(§12-2)에서 표시 이름도 함께 비교한다.
- **entity를 영어로 고정하지 않는 이유**
  - 동네 가게, 국내 브랜드처럼 영어 이름이 없는 대상이 많다. 억지로 로마자로 바꾸면 표기가 흔들리고 원래 이름이 사라진다.
- **entity 정규형 고르기**
  - 국내 가게·브랜드는 한국어(`성수 ○○카페`, `이마트`)로, 해외 고유명사는 원어(`GlenDronach`, `Hario V60`)로 둔다.
  - 국내에서 한국어 표기가 굳어진 해외 브랜드(`스타벅스`/`Starbucks`)처럼 애매한 경우는 처음 등록할 때 LLM이 정한 값을 고정한다. 다른 쪽 표기가 별칭에 있으면 매칭에는 영향이 없다.
- **매칭은 별칭이 맡는다**
  - 처음 등록할 때 LLM이 별칭을 함께 만든다. 다른 언어 표기, 줄임말, 흔한 오기다(`스벅`, `Starbucks`, `스타벅스커피`).
  - 저장된 정규형·별칭은 공백, 대소문자, 악센트, 문장부호만 정규화한다. 조사를 떼면 이름이 망가진다(`독도` → `독`).
  - 조사는 note나 질문에 나온 표기 쪽에서만, 등록된 이름과 가장 길게 맞는 형태를 찾는 방식으로 뗀다(`제주에서` → `제주`).
  - 별칭은 쌓아 간다. 새 note에서 기존 entity가 다른 표기로 나오고 같은 것으로 판정되면 그 표기를 별칭에 더한다.
- **언어가 다른 같은 entity가 두 번 등록되지 않게 한다**
  - 정규형 언어를 고정하지 않으니 `Jeju`와 `제주`가 따로 만들어질 수 있다.
  - 새 entity를 만들기 전에 후보를 찾고, LLM이 같은 것인지 판정한다.
    - 문자열 일치만으로는 언어가 다른 표기를 못 찾는다. `Jeju`가 새로 나왔을 때 `제주`의 별칭에 `Jeju`가 아직 없으면 걸리지 않는다.
    - 그래서 먼저 새 entity의 별칭(LLM이 만든 다른 언어 표기)이 등록된 entity의 정규형·별칭과 겹치는지 본다. 그래도 없으면 "이름 + 종류 + 짧은 설명"의 embedding으로 후보를 뽑는다.
    - 후보를 뽑는 방법만 다르고, 판정을 LLM이 하는 것은 등록된 tag의 동의어 병합(§12-2)과 같다.
  - 카탈로그에 그 장소 자체가 topic으로 있으면(국가 단위) topic id로도 묶는다. 한국 도시·섬처럼 국가 topic에만 연결되는 지명은 이것으로 묶을 수 없다.
- **질문 쪽**
  - 질문이 "스벅 리저브"든 "Starbucks Reserve"든 같은 entity에 맞아야 한다. 질문의 entity도 같은 정규화를 거쳐 정규형과 별칭으로 맞춘다. 맞는 것이 없으면 위의 후보 찾기로 뽑은 후보 entity를 LLM에게 주고 고르게 한다.
  - 실험 계획 E-1의 표기가 다른 질문에 한영이 섞인 경우를 넣었다.
- **표시:** 정규형이 원래 언어라 그대로 보여줘도 자연스럽다. 다만 상호명과 지명은 portal과 "왜 이 사람인지" 설명에 드러내지 않는다(§12-3).
- **아직 정하지 않은 것: 등록된 tag와 entity의 경계.** §11-1은 제품·브랜드·약 이름을 registry tag에 맡겼고, 실험의 등록된 tag에도 `glendronach`, `starbucks`, `galaxy s25 ultra` 같은 이름이 많다. §12-3은 장소에 더해 상품명과 상호명도 entity로 뽑는다. 둘 다 두면 같은 대상이 tag(`glendronach`)와 entity(`GlenDronach`)에 다른 표기로 생긴다. 상품·브랜드·상호명을 등록된 tag에서도 빼고 entity만 쓸지는 실험 계획 E에서 함께 본다.
  - 2026-10-29에 이름 tag를 사후로 빼 봤다(실험 문서 §14). 답하기는 그대로였다. shout 직접 경험자 hit@5는 −0.042로, 질문 95개로는 판단 불가였다. 이름은 주로 "작게" 단계를 채우던 tag라서, 빼면 "작게"가 빈 질문이 43%에서 58%로 는다. 그래서 entity가 이 단계를 대신 채울 수 있는지가 E에서 볼 것 중 하나다.
  - 이름 분류는 tag 이름과 정의만 보고 했다. note를 함께 읽히면 더 잘 가를 수 있다(오너 의견). E의 entity 뽑기 프롬프트에 반영한다.
